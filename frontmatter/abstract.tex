% WebAssembly (Wasm) is a binary instruction format originally designed for web browsers that provides a portable, high-performance execution environment. It enables web browsers to execute code written in more than 40 programming languages seamlessly, delivering high performance across different platforms. While Wasm’s use on the client side is well known, with the introduction of the WebAssembly System Interface (WASI), its deployment on the server side has recently gained traction, especially in containerized environments managed in Kubernetes clusters. However, integrating Wasm into container runtimes presents challenges related to concurrency under WASI Preview~1~(P1), efficient use of multi-core CPU architectures, developer experience, and ecosystem maturity.

% While Docker remains the de facto standard for containerization in Kubernetes environments, its relatively high resource consumption and startup times can be limiting, especially in scenarios that require rapid scaling or high efficiency. In contrast, WebAssembly promises a more lightweight execution model, with near-instant startup and reduced memory usage.

% This thesis explores the memory efficiency/footprint, cold and warm start-up times, security and performance trade-offs introduced by running Rust and TinyGo code in a Wasm runtime, the ecosystem maturity, and the development experience of Wasm versus conventional Linux containers deployed with Docker. It also analyzes maintainability and operational complexity for real-world cloud deployments and provides recommendations and best practices for adopting WebAssembly in cloud-native environments.

% The findings of the thesis indicate that Wasm containers feature significantly lower image sizes than Docker containers (0.13\,MB for Rust/Wasm vs.\ 6\,MB for Go/Docker) and achieve comparable cold-start times to Docker for image-cached warm starts. However, due to WASI~P1’s lack of multi-threaded I/O primitives, the WASM-based services are constrained to single-threaded request handling, leading to significantly increased latencies and reduced throughput under concurrent load compared to conventional containers. Furthermore, libraries that depend on OS-specific features absent from WASI~P1---such as POSIX thread spawning, native networking sockets beyond runtime-specific extensions, and C++ exceptions---cannot be directly compiled to Wasm, which limits the available dependency ecosystem. The Kubernetes integration for Wasm also requires non-standard cluster setup (compiling crun from source, custom containerd configuration) that is not available in managed cloud Kubernetes offerings without custom node groups. Nevertheless, the current technology limitations of WASI~P1 still present more operational challenges than benefits compared to conventional Docker containers for developing high-concurrency microservices in today’s rapidly evolving market. Wasm is best suited for stateless, low-concurrency, density-critical workloads where cold-start speed and image size are primary concerns.
