\chapter*{Abstract}
\addcontentsline{toc}{chapter}{Abstract}
\begin{otherlanguage*}{american}

\begin{sloppypar}
Cloud-native microservices increasingly run at the edge, scale to zero between requests, and pack many tenants onto a single node. In all three settings, image footprint and cold-start latency become first-order constraints rather than nice-to-haves. The conventional Docker and \texttt{runc} stack pays a baseline cost on every instance because each container carries an OS userland alongside the application. WebAssembly together with the WebAssembly System Interface offers a complementary execution model. It promises smaller artefacts, faster startup, and a capability-bounded sandbox without that userland tax. The practical question this thesis answers is whether server-side WebAssembly is, today, a viable alternative to Docker for production HTTP microservices in Kubernetes.
\end{sloppypar}

The study is a controlled side-by-side comparison in upstream Kubernetes on a single dedicated cloud node. Four implementation variants are evaluated in a $2 \times 2$ matrix that crosses the runtime axis (Docker vs.\ WebAssembly) with the language-family axis (Rust vs.\ Go-family). Each variant is exercised under four workload regimes that span the dominant shapes of stateless HTTP services: CPU-bound compute, memory-bandwidth pressure, I/O-bound outbound fan-out, and JSON serialization. Measurements cover five quantitative metrics and one qualitative developer-experience assessment. Concrete tool versions and deployment specifics are deferred to the implementation chapter.

The results confirm WebAssembly's structural advantages on the static axes. Wasm artefacts are roughly an order of magnitude smaller than their Docker counterparts on every workload measured. Cold-start latency converges for both Wasm variants and the minimal-base Docker variant. The cold-start advantage often attributed to Wasm in general is therefore a property shared with scratch-based containers. Under sustained load, however, the runtime gap is workload-class-sensitive rather than constant. It narrows almost to parity on the serialization regime and sits modestly behind the fastest Docker baseline on the CPU- and memory-bandwidth regimes. On the I/O-bound fan-out regime, the gap widens visibly because async-dispatch maturity becomes the differentiator. The TinyGo path lags on every regime, because its WASI Preview 1 runtime cannot express concurrent outbound dispatch. End-to-end latency percentiles track the same per-regime ordering.

The qualitative assessment reaches a similar conclusion. Dependency compatibility on the SpinKube path is at parity with Docker. However, toolchain setup, Kubernetes integration, and live debugging cost materially more effort on the Wasm side. Operationally, getting a Wasm service to production-grade reliability still demands more from the team than an equivalent Docker container. The thesis concludes that, notwithstanding Wasm's clear wins on image size and cold-start density, \textbf{Docker remains the more mature and productive default for general-purpose microservice architectures in Kubernetes today}. Server-side Wasm with SpinKube and WASI Preview~2 is a strong choice for narrow workload classes where its structural advantages outweigh its current ecosystem limitations.
