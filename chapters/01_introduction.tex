\chapter{Introduction}
\label{chap:introduction}

\section{Context}
The modern cloud computing landscape relies heavily on microservices and containerization to deliver scalable, resilient applications. Docker and the \ac{OCI} standards, frequently paired with mature backend languages like Golang, have become the de facto foundation for these deployments within \ac{K8s} environments~\cite{merkel2014docker, burns2016borg}. This traditional cloud-native stack prioritizes a frictionless developer experience and mature tooling. However, the growing demand for edge computing, high-density serverless functions, and instantaneous scaling has exposed the architectural limitations of conventional Linux containers. \ac{OCI} containers rely on operating-system-level virtualization, which carries a baseline overhead in both memory consumption and initialization time~\cite{shillaker2020faasm}.

As organizations seek to maximize hardware utilization and minimize latency, a shift toward more lightweight execution environments is underway. \ac{Wasm}, originally designed as a highly optimized, stack-based virtual machine binary format for web browsers~\cite{haas2017bringing}, has emerged as a potential solution for server-side workloads. With the introduction of the \ac{WASI}, \acs{Wasm} promises a portable, secure, and near-instantaneous execution model that operates without the heavy dependencies of a traditional Linux container~\cite{clark2019standardizing}. As illustrated in Figure~\ref{fig:thesis_overview}, this thesis evaluates four implementation variants spanning two runtime paths within a single \acs{K8s} cluster.

\section{Problem Statement}
Standard \ac{OCI} containers introduce measurable overhead regarding memory footprint and cold-start latency. While negligible for traditional monolithic applications, this overhead becomes a severe limiting factor for transient microservices that require rapid, sub-millisecond scaling. The emerging \acs{Wasm} stack theoretically solves this by utilizing \ac{SFI} to strip away the operating system layer entirely, offering drastically reduced image sizes and high-density execution~\cite{gadepalli2020challenges}.

However, transitioning from a mature ecosystem to a nascent one introduces substantial, often under-documented friction. The core problem this thesis addresses is the tension between computational efficiency and developer velocity. While the \acs{Wasm} ecosystem promises high performance for server-side workloads, its current \acs{WASI} Preview~1~(P1) runtime environment does not expose multi-threaded \ac{HTTP} primitives, constraining concurrent request handling to single-threaded execution models~\cite{clark2019standardizing, sondell2024performance}. Furthermore, libraries that depend on \ac{OS}-specific features absent from \acs{WASI}~P1---such as \ac{POSIX} thread spawning, native networking sockets beyond runtime-specific extensions, and C++ exceptions---cannot be directly compiled to \acs{Wasm}, limiting the available dependency ecosystem~\cite{liu2025wasmcontainer, kjorveziroski2023serverless}.

There is a critical need to empirically quantify the holistic trade-offs of these two paradigms. It must be determined whether the theoretical efficiency gains of the \acs{Wasm} stack outweigh the practical performance degradations and the operational complexities it introduces compared to the industry-standard Docker baseline.

\section{Research Questions}
To address the problem statement, this thesis investigates the following primary research questions:
\begin{itemize}
    \item \textbf{RQ1:} How does the memory footprint and \acs{OCI} artifact size of the SpinKube/Wasmtime \acs{Wasm} stack compare to a Docker/\texttt{runc} baseline in a single-node \acs{K8s} cluster?
    \item \textbf{RQ2:} To what extent do \acs{Wasm} runtimes improve cold- and warm-start latency compared to \acs{OCI} containers executed under \texttt{runc}, across both garbage-collected (Go) and ahead-of-time-compiled (Rust) baselines?
    \item \textbf{RQ3:} What are the runtime performance trade-offs---specifically request throughput and end-to-end latency---introduced by SpinKube's \acs{WASI}~P2 single-component dispatch model (one request per Wasmtime instance at a time) compared to Docker/\texttt{runc}-based concurrency models?
    \item \textbf{RQ4:} How do the current \acs{Wasm}-on-Kubernetes ecosystem (SpinKube, the \acs{WASI}~Preview~1 / Preview~2 toolchains, library compatibility) and operational integration impact developer experience compared to a mature Docker/\acs{K8s} workflow?
\end{itemize}

\section{Research Methodology}
This research employs a mixed-methods approach, combining quantitative performance benchmarking with a qualitative assessment of developer experience.

Rather than isolating the runtime---which would necessitate comparing equivalent languages and thereby destroying the ability to measure real-world developer experience---this study compares two dominant paradigms in their native contexts using four implementation variants. A baseline microservice is developed using Golang and compiled into a standard Linux-based Docker image, and a second baseline uses Rust with Docker to partially deconfound the language variable. Two experimental variants compile functionally equivalent services to \acs{WASI}-compliant \acs{Wasm} modules: one using Rust and one using TinyGo. All four artifacts are deployed into an isolated \acs{K8s} test cluster utilizing \texttt{containerd}, standard \texttt{runc}, and a \acs{Wasm} shim.

Quantitative data is gathered by subjecting all deployments to standardized load testing. Monitoring tools measure cold-start times, memory consumption, \acs{CPU} utilization, throughput, and request latency. The approach acknowledges that language-level differences (e.g., Go's garbage collection versus Rust's manual memory management) influence the metrics, but is designed to reflect the real-world performance delta an engineering team experiences when transitioning between these technological stacks. A qualitative analysis is also conducted on the development lifecycle, documenting compilation friction, library compatibility, and pipeline integration complexity.

\section{Thesis Contributions}
This thesis provides the following key contributions to the field of cloud-native architecture:
\begin{enumerate}
    \item \textbf{Holistic Paradigm Benchmark:} A side-by-side performance comparison of the Golang/Docker stack versus the Rust/\acs{Wasm} stack, highlighting specific metrics where the \acs{Wasm} ecosystem succeeds (density, initialization) and where it currently falls short (throughput, concurrent request handling) due to \acs{WASI}~P1 ecosystem constraints.
    \item \textbf{Developer Experience Assessment:} A critical evaluation of the current state of \acs{Wasm} for backend development, quantifying the engineering friction of compiling Rust and TinyGo code to \acs{WASI} and navigating incompatible library dependencies compared to standard Go and Docker development.
    \item \textbf{Adoption Framework:} Actionable recommendations for cloud architects, delineating specific use cases where the \acs{Wasm} stack is currently viable and identifying the operational risks that make it unsuitable for rapid-iteration product teams accustomed to the Go/Docker ecosystem.
\end{enumerate}

The remainder of this thesis is structured as follows:
\begin{itemize}
    \item \hyperref[chap:background]{\textbf{Chapter~\ref{chap:background}: Background}} provides the foundational technical context on cloud computing paradigms, containerization technologies, and the evolution of \acs{Wasm} and \acs{WASI}---including the Component Model, available runtimes, and the \acs{K8s} integration landscape.
    \item \hyperref[chap:state_of_the_art]{\textbf{Chapter~\ref{chap:state_of_the_art}: Related Work}} surveys peer-reviewed performance studies comparing server-side \acs{Wasm} and container workloads, security analyses, and compiler strategy trade-offs, and additionally surveys the commercial deployment landscape of server-side \acs{Wasm} and concrete production deployments.
    \item \hyperref[chap:methodology]{\textbf{Chapter~\ref{chap:methodology}: Research Methodology}} defines the comparative analysis strategy, establishes the four implementation variants and their selection rationale, and outlines the precise measurement metrics.
    \item \hyperref[chap:implementation]{\textbf{Chapter~\ref{chap:implementation}: Implementation}} details the cloud infrastructure setup, benchmark service design, all four service implementations, and the \acs{K8s} cluster configuration for hybrid \acs{Wasm} and Docker workloads.
    \item \hyperref[chap:evaluation]{\textbf{Chapter~\ref{chap:evaluation}: Evaluation}} presents the quantitative benchmark results for the prime sieve benchmark alongside the qualitative assessment of developer experience.
    \item \hyperref[chap:discussion]{\textbf{Chapter~\ref{chap:discussion}: Discussion and Future Work}} analyzes the trade-offs between technological maturity, computational efficiency, and developer velocity, and outlines planned future experiments.
    \item \hyperref[chap:conclusion]{\textbf{Chapter~\ref{chap:conclusion}: Conclusion}} summarizes the core findings and final verdicts of the research.
\end{itemize}
