\chapter{Introduction}
\label{chap:introduction}

\section{Context}
The modern cloud computing landscape relies heavily on microservices and containerization to deliver scalable, resilient applications. Docker and the \ac{OCI} standards, frequently paired with mature backend languages like Golang, have become the de facto foundation for these deployments within \ac{K8s} environments~\cite{merkel2014docker, burns2016borg}. This traditional cloud-native stack prioritizes a frictionless developer experience and mature tooling. However, the growing demand for edge computing, high-density serverless functions, and instantaneous scaling has exposed the architectural limitations of conventional Linux containers. \ac{OCI} containers rely on operating-system-level virtualization, which carries a baseline overhead in both memory consumption and initialization time~\cite{shillaker2020faasm}.

As organizations seek to maximize hardware utilization and minimize latency, a shift toward more lightweight execution environments is underway. \ac{Wasm}, originally designed as a highly optimized, stack-based virtual machine binary format for web browsers~\cite{haas2017bringing}, has emerged as a potential solution for server-side workloads. With the introduction of the \ac{WASI}, \acs{Wasm} promises a portable, secure, and near-instantaneous execution model that operates without the heavy dependencies of a traditional Linux container~\cite{clark2019standardizing}. As illustrated in Figure~\ref{fig:thesis_overview}, this thesis evaluates four implementation variants spanning two runtime paths within a single \acs{K8s} cluster.

\section{Problem Statement}
Standard \ac{OCI} containers introduce measurable overhead regarding memory footprint and cold-start latency. While negligible for traditional monolithic applications, this overhead becomes a severe limiting factor for transient microservices that require rapid, sub-millisecond scaling. The emerging \acs{Wasm} stack theoretically solves this by utilizing \ac{SFI} to strip away the operating system layer entirely, offering drastically reduced image sizes and high-density execution~\cite{gadepalli2020challenges}.

\begin{sloppypar}
However, transitioning from a mature ecosystem to a nascent one introduces substantial, often under-documented friction. The core problem this thesis addresses is the tension between computational efficiency and developer velocity. The server-side \acs{Wasm} ecosystem now spans two specification generations. \acs{WASI} Preview~1 still exposes only single-threaded execution to \acs{Wasm} modules~\cite{clark2019standardizing, sondell2024performance}, while \acs{WASI} Preview~2 introduces a request-handler dispatch model and the \texttt{wasi:io/poll} event-loop that allow a single component instance to interleave multiple in-flight requests at I/O suspension points~\cite{clark2023preview2, bytecodealliance2024componentmodel}. True intra-component multithreading is not yet part of either preview~\cite{clark2023preview2, bytecodealliance2024componentmodel}. Per-pod concurrency is therefore bounded, and additional concurrency is gained by scaling pod replicas rather than by spawning threads inside the component. Language tooling maturity compounds the picture in workload-specific ways. The Rust path compiles standard Tokio-style async code to a \acs{WASI}~P2 component largely unmodified. The TinyGo path remains pinned to \acs{WASI}~P1 because TinyGo's \texttt{wasip2} target hardwires the \texttt{wasi:cli/command} world, and its standard-library coverage of concurrency primitives is still rough enough that idioms such as \texttt{sync.WaitGroup} can fail at runtime~\cite{liu2025wasmcontainer, kjorveziroski2023serverless}. Whether these constraints translate into a meaningful performance penalty in practice depends on the workload class, and that dependency is what this thesis sets out to measure.
\end{sloppypar}

There is a critical need to empirically quantify the holistic trade-offs of these two paradigms. It must be determined whether the theoretical efficiency gains of the \acs{Wasm} stack outweigh the practical performance degradations and the operational complexities it introduces compared to the industry-standard Docker baseline.

\section{Research Questions}
To address the problem statement, this thesis investigates the following primary research questions. RQ1 and RQ2 concern static artefact and lifecycle properties that travel uniformly across workload classes. RQ3 is examined across four workload regimes (\acs{CPU}-bound, memory-bandwidth, I/O-bound HTTP fan-out, and \acs{JSON} serialization) because the runtime trade-offs vary materially by regime. RQ4 captures the developer-experience axis that is independent of workload choice.
\begin{itemize}
    \item \begin{sloppypar}\textbf{RQ1:} How does the memory footprint and \acs{OCI} artifact size of the SpinKube/Wasmtime \acs{Wasm} stack compare to a Docker/\texttt{runc} baseline in a single-node \acs{K8s} cluster?\end{sloppypar}
    \item \begin{sloppypar}\textbf{RQ2:} To what extent do \acs{Wasm} runtimes improve cold- and warm-start latency compared to \acs{OCI} containers executed under \texttt{runc}, across both garbage-collected (Go) and ahead-of-time-compiled (Rust) baselines?\end{sloppypar}
    \item \begin{sloppypar}\textbf{RQ3:} What are the runtime performance trade-offs---specifically request throughput and end-to-end latency---introduced by SpinKube's \acs{WASI}~P2 single-component dispatch model (one request per Wasmtime instance at a time) compared to Docker/\texttt{runc}-based concurrency models, and how does the size of the trade-off vary across the \acs{CPU}-bound, memory-bandwidth, I/O-bound, and serialization workload regimes?\end{sloppypar}
    \item \textbf{RQ4:} How do the current \acs{Wasm}-on-Kubernetes ecosystem (SpinKube, the \acs{WASI}~Preview~1 / Preview~2 toolchains, library compatibility) and operational integration impact developer experience compared to a mature Docker/\acs{K8s} workflow?
\end{itemize}

\section{Research Methodology}
This research employs a mixed-methods approach, combining quantitative performance benchmarking with a qualitative assessment of developer experience.

\begin{sloppypar}
Rather than isolating the runtime---which would necessitate comparing equivalent languages and thereby destroying the ability to measure real-world developer experience---this study compares two dominant paradigms in their native contexts using four implementation variants. A baseline microservice is developed using Golang and compiled into a standard Linux-based Docker image. A second baseline uses Rust with Docker to partially deconfound the language variable. Two experimental variants compile functionally equivalent services to \acs{WASI}-compliant \acs{Wasm} modules: one using Rust and one using TinyGo. All four artifacts are deployed into an isolated \acs{K8s} test cluster utilizing \texttt{containerd}, standard \texttt{runc}, and a \acs{Wasm} shim.
\end{sloppypar}

Quantitative data is gathered by subjecting all deployments to standardized load testing. Monitoring tools measure cold-start times, memory consumption, \acs{CPU} utilization, throughput, and request latency. The approach acknowledges that language-level differences (e.g., Go's runtime tracing garbage collector versus Rust's compile-time ownership-and-borrowing model with deterministic \acs{RAII} destruction) influence the metrics. However, the design reflects the real-world performance delta an engineering team experiences when transitioning between these technological stacks. A qualitative analysis is also conducted on the development lifecycle, documenting compilation friction, library compatibility, and pipeline integration complexity.

\section{Thesis Contributions}
This thesis provides the following key contributions to the field of cloud-native architecture:
\begin{enumerate}
    \item \textbf{Holistic Paradigm Benchmark:} A side-by-side performance comparison of the Golang/Docker, Rust/Docker, Rust/\acs{Wasm}, and TinyGo/\acs{Wasm} stacks across four workload regimes (\acs{CPU}-bound prime sieve, memory-bandwidth, I/O-bound HTTP fan-out, and \acs{JSON} round-trip), highlighting where the \acs{Wasm} ecosystem succeeds under \acs{WASI}~Preview~2 with Spin's request-handler dispatch (artefact density, cold-start parity with minimal-base containers, on-par serialization throughput) and where it still trails (concurrent outbound dispatch on the TinyGo/\acs{WASI}~P1 path, wider p99 tail under JIT compilation).
    \item \textbf{Developer Experience Assessment:} A critical evaluation of the current state of \acs{Wasm} for backend development, quantifying the engineering friction of compiling Rust and TinyGo code to \acs{WASI} and navigating incompatible library dependencies compared to standard Go and Docker development.
    \item \textbf{Adoption Framework:} Actionable recommendations for cloud architects, delineating specific use cases where the \acs{Wasm} stack is currently viable and identifying the operational risks that make it unsuitable for rapid-iteration product teams accustomed to the Go/Docker ecosystem.
\end{enumerate}

\section{Thesis Structure}
The remainder of this thesis is structured as follows:
\begin{itemize}
    \item \hyperref[chap:background]{\textbf{Chapter~\ref{chap:background}: Background}} provides the foundational technical context on cloud computing paradigms, containerization technologies, and the evolution of \acs{Wasm} and \acs{WASI}---including the Component Model, available runtimes, and the \acs{K8s} integration landscape.
    \item \hyperref[chap:state_of_the_art]{\textbf{Chapter~\ref{chap:state_of_the_art}: Related Work}} surveys peer-reviewed performance studies comparing server-side \acs{Wasm} and container workloads, security analyses, and compiler strategy trade-offs, and additionally surveys the commercial deployment landscape of server-side \acs{Wasm} and concrete production deployments.
    \item \hyperref[chap:methodology]{\textbf{Chapter~\ref{chap:methodology}: Research Methodology}} defines the comparative analysis strategy, establishes the four implementation variants and their selection rationale, and outlines the precise measurement metrics.
    \item \hyperref[chap:implementation]{\textbf{Chapter~\ref{chap:implementation}: Implementation}} details the cloud infrastructure setup, benchmark service design, all four service implementations, and the \acs{K8s} cluster configuration for hybrid \acs{Wasm} and Docker workloads.
    \item \hyperref[chap:evaluation]{\textbf{Chapter~\ref{chap:evaluation}: Evaluation}} presents the quantitative benchmark results across the four workload regimes (prime sieve, memory bandwidth, HTTP fan-out, and \acs{JSON} round-trip) alongside the qualitative assessment of developer experience.
    \item \hyperref[chap:discussion]{\textbf{Chapter~\ref{chap:discussion}: Discussion and Future Work}} analyzes the trade-offs between technological maturity, computational efficiency, and developer velocity, and outlines planned future experiments.
    \item \hyperref[chap:conclusion]{\textbf{Chapter~\ref{chap:conclusion}: Conclusion}} summarizes the core findings and final verdicts of the research.
\end{itemize}
