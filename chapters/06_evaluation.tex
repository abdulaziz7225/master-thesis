The wasm-rust image (0.13\,MB) is the smallest by a large margin: it is 16$\times$ smaller than docker-rust (2.08\,MB) despite both using the same language and algorithm, and 46$\times$ smaller than docker-golang (6.00\,MB). This dramatic reduction reflects the \acs{Wasm} binary format's elimination of \acs{OS} userland, libc, dynamic linker, and \acs{ELF} binary overhead. The \texttt{.wasm} file contains only compiled application logic; all runtime infrastructure is provided by \acs{WasmEdge} on the host.

Unexpectedly, wasm-tinygo (2.26\,MB) is \textit{larger} than docker-rust (2.08\,MB) despite also targeting \acs{Wasm}. TinyGo bundles its own minimal Go runtime---scheduler stub, conservative garbage collector, and standard library subset---directly inside the \texttt{.wasm} binary. This is an inherent cost of Go's garbage-collected memory model: the \acs{GC} machinery cannot be stripped out. By contrast, the wasm-rust binary has no runtime and no \acs{GC}, accounting for its near-zero overhead.

The docker-golang image (6.00\,MB) uses a \texttt{scratch} base and contains only the statically-linked binary; the overhead compared to docker-rust (2.08\,MB) reflects Go's compiled-in runtime metadata---goroutine scheduler, garbage collector, and standard library \acs{DWARF} symbols.

\textbf{Practical implication:} At high replica densities (e.g.\ 1\,000 pod instances), the wasm-rust variant saves $\approx$5.87\,GB of registry transfer and node-local image storage per pull cycle compared to docker-golang, directly reducing cold-start time in autoscaling scenarios where images are not pre-cached.

This is a characteristic of Go's managed runtime, not of Docker itself.

\subsection{Docker Variants}

Both Docker variants achieve high throughput with zero failures. docker-golang (509.6\,\acs{RPS}) slightly outperforms docker-rust (479.5\,\acs{RPS}) in raw throughput, but docker-rust achieves lower p95 latency (157.6\,ms vs.\ 196.3\,ms), reflecting axum/Tokio's deterministic async scheduling compared to Go's work-stealing goroutine scheduler under high contention.

The \texttt{server\_compute\_us} metric---the server-side wall-clock time of the sieve computation alone---is 752\,$\mu$s median for docker-golang and 1002\,$\mu$s median for docker-rust. Both are in the sub-millisecond range, confirming that the sieve algorithm compiles and executes efficiently as native code on both runtimes. The docker-golang p95 compute time is 32.3\,ms (vs.\ the 1.5\,ms p95 for docker-rust), reflecting bursty \acs{CPU} contention when many goroutines are scheduled concurrently on only 2 vCPUs: Go's work-stealing scheduler occasionally places multiple sieve computations on the same core, inflating the wall-clock time for those goroutines.

\subsection{Wasm Variants: The WASI P1 Concurrency Bottleneck}

The Wasm variants tell a fundamentally different story. wasm-rust achieves only 24.0\,\acs{RPS} with a 67.1\% failure rate (1\,471 failed requests out of 2\,192 total). wasm-tinygo is worse still: 2.9\,\acs{RPS} with a 47.9\% failure rate and a p95 latency of 18.7\,s.

\textbf{Root cause: architectural, not algorithmic.} The \texttt{server\_compute\_us} metric exposes the real situation. wasm-rust records a median compute time of 117.5\,ms per sieve execution; wasm-tinygo records 243.9\,ms. These figures are 156$\times$ and 324$\times$ slower than their Docker counterparts for the same algorithm.

This performance gap arises from two compounding factors:

\begin{enumerate}
    \item \textbf{\acs{WASI} P1 single-threaded execution.} As documented in \hyperref[chap:implementation]{Chapter~\ref{chap:implementation}}, both Wasm variants operate a blocking, single-threaded \texttt{accept()}-handle-respond loop. Under 50 concurrent \acp{VU}, incoming connections queue at the \acs{TCP} level. The first accepted request runs to completion before the second is accepted. Connections that wait longer than k6's default timeout are reported as failures. This explains the high failure rates and multi-second p95 latencies.

    \item \textbf{\acs{WasmEdge} \acs{JIT} overhead for array-intensive workloads.} The sieve algorithm performs dense, indexed access over a boolean array of 100\,000 elements. \acs{Wasm}'s \acl{SFI} model requires that every memory access be bounds-checked at runtime. Although \acs{WasmEdge}'s \acs{LLVM} \acs{JIT} eliminates many redundant checks via range analysis, the inner-loop access pattern of the sieve---where the index is a non-trivial linear expression of two loop variables---limits how aggressively the JIT can hoist or eliminate bounds checks. The result is a significant \acs{CPU} overhead per sieve execution compared to native code, where the compiler has complete visibility and can eliminate all bounds checks statically.
\end{enumerate}

\textbf{wasm-rust vs.\ docker-rust (language-controlled comparison).} Both variants use identical Rust source code for the sieve algorithm. The sole difference is the execution environment. wasm-rust at 24.0\,\acs{RPS} vs.\ docker-rust at 479.5\,\acs{RPS} represents a 20$\times$ throughput gap attributable jointly to (1) the \acs{WASI} P1 single-threaded I/O constraint and (2) \acs{WasmEdge} \acs{JIT} bounds-checking overhead on array-intensive computation. Disentangling the relative contributions of these two factors would require running wasm-rust on a \acs{WASI} P2 runtime with multi-threaded I/O, which is left as future work.

\textbf{wasm-tinygo vs.\ wasm-rust.} Both Wasm variants face the same concurrency constraint, yet wasm-tinygo's median server compute time (243.9\,ms) is 2.1$\times$ higher than wasm-rust's (117.5\,ms). TinyGo's conservative garbage collector introduces additional overhead for the boolean array allocation: the conservative scan must treat every word on the stack as a potential pointer, inflating the cost of heap operations. The sieve allocates a fresh \texttt{[]bool} slice on each request; under TinyGo's conservative \acs{GC}, this allocation and its subsequent scan are more expensive than Rust's stack-allocated \texttt{Vec<bool>}, which the Rust allocator handles without any garbage collection overhead.

\subsection{Saturation Analysis}

wasm-rust's theoretical single-threaded throughput ceiling is $1000\,\text{ms} / 117.5\,\text{ms} \approx 8.5$\,\acs{RPS}. The observed 24.0\,\acs{RPS} exceeds this ceiling, which can be explained by k6's connection keep-alive behaviour: once a connection is established, the \acs{TCP} overhead for subsequent requests on the same connection is minimal, and the server can pipeline the response to a fast client before the accept loop cycles. The 67.1\% failure rate confirms that saturation has been reached---the \acs{TCP} queue fills up faster than connections are drained.

wasm-tinygo's ceiling is $1000\,\text{ms} / 243.9\,\text{ms} \approx 4.1$\,\acs{RPS}$. The observed 2.9\,\acs{RPS} falls below this ceiling, consistent with the very high \texttt{http\_req\_blocked} times (p90: 5.1\,s) indicating that connections are waiting at the \acs{OS} \acs{TCP} stack before even being accepted by the server process.

\textbf{Memory.} docker-rust has the lowest \acs{RSS} (2.02\,MB idle, 2.26\,MB peak), reflecting the absence of a garbage collector and the minimal Tokio async runtime footprint. wasm-rust is higher (4.38\,MB idle), despite using the same language, because \acs{WasmEdge} allocates its \acs{JIT} compilation context and \acs{Wasm} linear memory region alongside the process. The \acs{JIT}-compiled native code and module metadata reside in \acs{WasmEdge}'s internal heap, which is counted in the container's \acs{RSS}. The negligible difference between idle and peak for wasm-rust (4.38 vs.\ 4.40\,MB) reflects the sieve's deterministic memory usage: the boolean array is allocated and freed on each request with no net growth.

docker-golang's idle \acs{RSS} of 13.63\,MB reflects the Go runtime's pre-allocated heap arena, goroutine stacks, and \acs{GC} metadata. Notably, docker-golang's peak \acs{RSS} equals its idle \acs{RSS} (13.63\,MB): under 50 concurrent goroutines, Go's \acs{GC} keeps memory usage within the pre-allocated pool without growing the heap.

The wasm-tinygo idle \acs{RSS} could not be captured: the Prometheus scrape interval (5\,s) did not produce a data point in the 60\,s idle window for this variant, likely due to the pod's readiness probe timing relative to the scrape schedule. The peak \acs{RSS} of 34.92\,MB is surprisingly high for a \acs{Wasm} variant. This reflects the conservative \acs{GC}'s behaviour: TinyGo's conservative \acs{GC} does not compact the heap and does not eagerly release memory, so boolean arrays allocated on each request accumulate in the heap until a full collection cycle runs.

\textbf{\acs{CPU} utilisation.} docker-rust (299.9\,mcores) and docker-golang (287.4\,mcores) show the highest \acs{CPU} utilisation, which is expected---they successfully process 479--510 requests per second, keeping both vCPUs fully occupied. wasm-rust (221.9\,mcores) and wasm-tinygo (260.3\,mcores) show lower \acs{CPU} utilisation not because they are more efficient, but because they process far fewer requests. The single-threaded saturation means the server executes only one sieve at a time; the remaining \acs{CPU} capacity goes unused while connections queue in the \acs{TCP} stack.

\subsection{Toolchain Setup}

The Docker variants require only a standard \texttt{docker build} workflow. Go~1.26's toolchain is a single binary download; Rust~1.94 requires \texttt{rustup} but is well-documented and cross-platform. The wasm-rust variant adds the \texttt{wasm32-wasip1} target (\texttt{rustup target add}) but is otherwise a standard \texttt{cargo build}. The wasm-tinygo variant requires TinyGo~0.40.1 in addition to the regular Go toolchain, with no stable package manager distribution on Ubuntu (requires a manual \texttt{.tar.gz} install or manual apt pinning). The mismatch between TinyGo's supported standard library subset and the full Go standard library is not surfaced until compilation time, creating unexpected friction.

\subsection{Dependency Compatibility}

This dimension shows the starkest contrast. The Docker variants had no dependency issues: all crates and packages on their respective target triples are well-supported.

For wasm-rust, the failure cascade documented in \hyperref[chap:methodology]{Chapter~\ref{chap:methodology}} required evaluating four candidate \acs{HTTP} approaches before a working solution was found. \texttt{hyper\_wasi} and \texttt{tokio\_wasi} are unmaintained \acs{WasmEdge}-specific forks that fail to compile against current Rust versions. \texttt{std::net::TcpListener} returns \texttt{Err("Unsupported")} at runtime on \texttt{wasm32-wasip1}. The only viable path---\texttt{wasmedge\_wasi\_socket~0.5.5}---is a \acs{WasmEdge}-specific crate not available in the mainstream Rust ecosystem; any dependency that transitively uses standard library networking will still fail. This represents a significant ecosystem gap: for a practical production service, dependency vetting for \acs{WASI} P1 compatibility must be performed manually.

For wasm-tinygo, the situation is worse. TinyGo's \texttt{net/http} server code path has been non-functional on \texttt{wasip1} since version~0.28 (Netdev architecture regression). The solution required writing a custom \texttt{server.go} file that calls \acs{WasmEdge} host socket functions directly via \texttt{//go:wasmimport} directives---a low-level technique that bypasses TinyGo's own standard library entirely. Additionally, the \texttt{-gc=conservative} build flag is required to prevent the \acs{GC} from treating \texttt{unsafe.Pointer} values passed to \acs{WasmEdge} host functions as reclaimable. None of these constraints are documented in the TinyGo or \acs{WasmEdge} official documentation; they were discovered through iterative debugging.

\subsection{Kubernetes Integration}

Docker variants require standard \acs{K8s} manifests with no special configuration. The \acs{Wasm} variants require three non-standard additions: (1) \texttt{runtimeClassName: wasmedge} in the pod spec, (2) two pod annotations (\texttt{run.oci.handler: wasmedge}, \texttt{module.wasm.image/variant: compat}), and (3) a cluster-level \texttt{RuntimeClass} object with a node selector. More significantly, the \acs{K8s} node itself requires crun~v1.22 compiled from source with \texttt{--with-wasmedge}, a custom containerd configuration block, and the WasmEdge 0.14.1 shared library installed system-wide. This setup is not available in any managed \acs{K8s} offering (EKS, GKE, AKS) without custom node groups or operator-managed DaemonSets, limiting the operational portability of the \acs{Wasm} deployment model.

\subsection{Debugging and Observability}

Docker containers support the full debugging toolkit: \texttt{kubectl exec} for interactive shell access, \texttt{docker logs} for stdout/stderr, and native debuggers (Delve for Go, \texttt{rust-gdb} for Rust) can be attached to running processes. Standard profiling tools (\texttt{pprof}, \texttt{perf}) work without modification.

\acs{Wasm} pods support \textit{only} stdout/stderr log output. \texttt{kubectl exec} cannot open a shell into a \acs{Wasm} pod because the \acs{WASI} environment does not expose a shell binary or an interactive \acs{PTY} interface. No debugger can attach to a running \acs{WasmEdge} process, and no standard profiler captures \acs{Wasm} module execution. The absence of debugger support significantly increases the iteration cycle when diagnosing runtime failures---the only diagnostic signal available is what the application explicitly writes to stderr. DWARF debug info support and interactive debugger attachment are items on the \acs{WASI} P2 roadmap.

The results reveal a clear trade-off. \acs{Wasm} variants---specifically wasm-rust---offer compelling size and cold-start advantages (0.13\,MB image, 42\,ms warm start, 4.40\,MB peak \acs{RSS}) that are directly relevant to high-density, serverless, and autoscaling workloads. However, \acs{WASI} P1's single-threaded I/O model combined with \acs{WasmEdge}'s \acs{JIT} overhead for array-intensive computation renders the Wasm variants uncompetitive for the high-concurrency microservice scenario tested here: 24\,\acs{RPS} with a 67\% failure rate versus 510\,\acs{RPS} with zero failures for docker-golang.

These findings directly address the four research questions:
\begin{itemize}
    \item \textbf{RQ1 (Resource Efficiency):} wasm-rust achieves 46$\times$ smaller images and 3$\times$ lower peak \acs{RSS} than docker-golang. The \acs{Wasm} binary format eliminates all \acs{OS} userland overhead.
    \item \textbf{RQ2 (Startup Latency):} With image cached, wasm-rust and wasm-tinygo start in $\approx$42\,ms---on par with docker-rust. docker-golang's warm starts are unexpectedly slow (median 4917\,ms) due to Go runtime initialisation overhead on a resource-constrained \acs{VM}.
    \item \textbf{RQ3 (Runtime Performance):} Docker variants dominate under concurrent load. The Wasm performance gap is driven by \acs{WASI} P1's single-threaded concurrency model and \acs{WasmEdge} \acs{JIT} overhead, not by the \acs{Wasm} binary format or algorithm quality.
    \item \textbf{RQ4 (Developer Experience):} The Docker variants present no ecosystem friction. The Wasm variants require navigating unmaintained libraries (\texttt{hyper\_wasi}, \texttt{tokio\_wasi}), broken standard library abstractions (TinyGo \texttt{net/http}, Rust \texttt{std::net}), and non-standard \acs{K8s} cluster setup not available in managed cloud offerings.
\end{itemize}
