\section{Threats to Validity}
\label{sec:threats_to_validity}

Several design choices and environmental constraints limit the generalisability of the results reported in this thesis.

\textbf{Single-node cluster.} All four primary variants run on a single two-vCPU Hetzner Cloud \acs{VM} sharing the same kernel, network stack, and physical \acs{CPU}. In a production multi-node cluster, scheduling, inter-node networking latency, and \acs{NUMA} topology would introduce additional variance not captured here. The results therefore characterise single-pod, co-located performance rather than at-scale distributed behaviour.

\textbf{Noisy-neighbour effects.} Although each benchmark run measures only one variant at a time, the load generator (k6) and the observability stack (Prometheus, Grafana) share the same host as the \acs{SUT}. \acs{CPU} and memory pressure from these background processes may inflate latency measurements, particularly for variants where baseline system load represents a proportionally larger share of available resources.

\textbf{Single workload type (compute-bound only for primary results).} Quantitative results are currently available only for the \acs{CPU}-bound prime sieve benchmark. The memory-bandwidth workload (implemented in \texttt{benchmarks/02-memory-bandwidth/}) and the Volta Monte Carlo \acs{VaR} engine described in Section~\ref{sec:workload_design} have not yet been benchmarked on the SpinKube variants. Workloads dominated by file I/O, database access, or inter-service communication may exhibit a substantially different performance profile.

\textbf{Thread concurrency model.} The primary benchmark runs with resource-fairness constraints: \texttt{GOMAXPROCS=1} for docker-golang, \texttt{TOKIO\_WORKER\_THREADS=1} for docker-rust, and SpinApp \texttt{spec.replicas:~1} for the Spin variants (each \acs{WASI}~P1/P2 component is itself single-threaded per Wasmtime instance). This single-thread constraint ensures that the comparison isolates runtime overhead rather than concurrency model differences. A supplementary scaling experiment (Section~\ref{sec:eval_performance}) removes these constraints (GOMAXPROCS=4, TOKIO\_WORKER\_THREADS=4, SpinApp \texttt{spec.replicas:~4}) to measure how effectively each variant exploits the available 4-vCPU environment of the Hetzner ccx23 host.

\textbf{JIT-only compilation.} The Spin \acs{Wasm} variants use Wasmtime's default \acs{JIT} (Cranelift) compilation path. \acs{AOT} pre-compilation via \texttt{wasmtime compile} narrows the performance gap with native code; the results reported here therefore represent a conservative lower bound on attainable Wasmtime throughput. The trade-off is that \acs{JIT} preserves binary portability across architectures, which is the deployment model evaluated in this study.
