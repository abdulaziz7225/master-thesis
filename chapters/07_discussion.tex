\chapter{Discussion and Future Work}
\label{chap:discussion}

\section{The Trade-off: Maturity vs. Efficiency}
\label{sec:discussion_tradeoff}

The headline finding of Chapter~\ref{chap:evaluation} is that, under \acs{WASI}~P2 with Spin's event-loop dispatch, the runtime performance gap between \acs{Wasm} and \acs{OCI} containers on stateless \acs{HTTP} workloads is much smaller than earlier \acs{WASI}~P1 benchmarks projected. The four-variant spread is 2.3$\times$ on the prime sieve and 1.9$\times$ on the memory-bandwidth workload, against the ~10$\times$ gap reported by \textcite{sondell2024performance} under \acs{WASI}~P1. \texttt{wasm-rust} matches \texttt{docker-golang} to within 6\% on prime-sieve throughput in limited mode and marginally beats its p99 latency; the \acs{OCI} artifact-density advantage is roughly 30$\times$ (\texttt{wasm-rust} 0.20\,MB vs \texttt{docker-golang} 6.00\,MB) and 10$\times$ against the smallest Docker variant (\texttt{docker-rust} 2.08\,MB); cold-start latency converges to a ~25--35\,ms band across both \acs{Wasm} variants and \texttt{docker-rust}; and \texttt{wasm-rust} consumes substantially fewer \acs{CPU} cycles per request than \texttt{docker-rust} at comparable throughput (~414\,mcores vs ~1212\,mcores, Section~\ref{sec:eval_resources}). On the efficiency axis the \acs{Wasm} stack is no longer the lagging option that early Wasmtime-on-Kubernetes literature described.

The gap that remains is one of \emph{ecosystem maturity} rather than runtime efficiency. \texttt{kubectl exec} does not open a shell into a \acs{Wasm} pod because the \acs{WASI} environment does not expose an interactive \acs{PTY}; no native debugger can attach to a running Wasmtime process from outside the sandbox; the \acs{Wasm} variants pay a per-pod resident-memory tax of roughly 20\,MiB for Wasmtime's \acs{JIT} compilation context and the pre-allocated linear-memory region; and TinyGo's \texttt{wasip2} target hardwires the \texttt{wasi:cli/command} world, which forces \texttt{wasm-tinygo} onto \texttt{-target=wasip1} plus the Spin Go \acs{SDK}'s \acs{CGo} bridge to export \texttt{wasi:http/incoming-handler}. These are not arguments against \acs{Wasm}---they are the surface area along which the \acs{Wasm} community is actively iterating with the Component Model, the \acs{WASI}~P2 capability interfaces, and the second-generation language \acs{SDK}s---but they are the costs a team adopting SpinKube today carries. The framing inherited from the Docker-versus-\acs{Wasm} literature, in which the runtime overhead is the binding constraint, no longer matches the measurements. The binding constraint has moved up the stack to tooling, debugging, and library coverage.

\section{Security Implications}
\label{sec:discussion_security}

The isolation primitive evaluated throughout this thesis is \acf{SFI}: Wasmtime emits per-load and per-store bounds checks against each module's linear-memory region, so a memory-safety bug inside a \acs{Wasm} component cannot escape into host memory or into another component's memory. \acs{WASI}~P2 layers a \acf{POLA} capability surface on top of this primitive: a component sees only the \texttt{wasi:http}, \texttt{wasi:io}, \texttt{wasi:filesystem}, and \texttt{wasi:sockets} resources that its imports name, and the host explicitly hands those resources in at instantiation time. By contrast, a \texttt{runc}-backed Docker container runs a full Linux process whose syscall surface is the complete kernel \acs{ABI} minus whatever seccomp and AppArmor profiles the cluster operator has configured; the container's process by default runs as \texttt{uid~0} inside the namespace, and the \acs{OCI} runtime offers no native equivalent to \acs{WASI}'s import-time capability handles. The two models are not in the same class: \acs{SFI} plus \acs{POLA} expresses what a handler is allowed to reach as part of the artifact's declared interface, where Docker expresses it as out-of-band cluster policy.

The operational consequence is that, for the multi-tenant edge and serverless deployment shape SpinKube targets, the ``deny-by-default'' capability surface reduces the blast radius of a compromised handler to whatever the \texttt{SpinApp} \acs{CRD} declared---which is in turn the only attestable surface the host needs to vouch for. This is the structural reason \acs{Wasm} composes cleanly with the \acf{TEE} stacks discussed in Section~\ref{sec:future_work_tee}, and the reason the small-\acs{TCB} argument from \textcite{menetrey2021twine, menetrey2022watz} generalises to the SpinKube deployment model rather than remaining confined to bespoke enclave-runtime research prototypes. Two caveats temper this view. First, \acs{SFI} addresses \emph{what a faulty module can reach inside its sandbox}---it does not address kernel-level isolation \emph{between} pods, which still rests on the underlying container runtime (\texttt{runc} or the \texttt{containerd-shim-spin-v2} process the Spin pod ultimately wraps). The two isolation primitives are stacked, not redundant. Second, the security gains are realised only if the \texttt{SpinApp} import list and the pod's \texttt{ServiceAccount}/RBAC posture are both tightened; an overly permissive \texttt{SpinApp} that imports the full \acs{WASI}~P2 world erodes the capability advantage in the same way that a Docker container running with \texttt{--privileged} erodes the namespace advantage.

\section{Migration Recommendations}
\label{sec:discussion_migration}

The measurements in Chapter~\ref{chap:evaluation}, combined with the trade-off framing of Section~\ref{sec:discussion_tradeoff} and the security framing of Section~\ref{sec:discussion_security}, support the following deployment guidance for a team weighing SpinKube/\acs{Wasm} against a Docker/\texttt{runc} baseline.

Adopt the SpinKube/\acs{Wasm} stack first for stateless \acs{HTTP} request handlers: the ~0.20\,MB \texttt{wasm-rust} artifact, the cold-start parity with minimal-base Docker images, and the lower \acs{CPU}-per-request profile compound directly into scale-to-zero cost savings and into higher pod density per node. The deployment shape Cloudflare Workers and Fastly Compute already host in production~\cite{cloudflare2024workers, fastly2024compute}---ephemeral request-handler functions with no long-lived state---is precisely where the measured advantages line up with the runtime model. Multi-tenant platforms gain a second benefit from the capability-bounded \acs{SFI} sandbox: the attack surface a compromised handler can reach is reduced to the \texttt{wasi:*} imports declared in the \texttt{SpinApp}, smaller and more attestable than the default-root namespace surface of a stock Docker container.

Keep workloads on Docker / \texttt{runc} when at least one of the following holds: the service maintains long-lived connections, WebSocket sessions, or stateful sagas that Spin's request-handler dispatch model does not represent; the workload depends on \acs{WASI} interfaces that are not yet exposed by \acs{WASI}~P2 in a stable form (raw \texttt{wasi:sockets} access patterns, fine-grained filesystem syscalls, native subprocess management); or the team's diagnostic workflow leans on \texttt{kubectl exec}, attached debuggers, or core-dump inspection---tooling that the \acs{WASI} execution model does not yet provide an equivalent for. \texttt{docker-rust} additionally remains the resident-memory champion in this study (~1--3\,MiB per pod), so memory-constrained packing densities still favour the minimal-scratch Docker variant over the ~20\,MiB linear-memory tax that every Spin pod carries.

The pragmatic recommendation is therefore not ``switch everything'' but ``switch the request-handler tier first''. Long-running stateful services keep their existing Docker / \texttt{runc} deployment path and the operator familiarity that comes with it; new ephemeral request handlers move onto SpinKube where the artifact-size, cold-start, and security advantages compound, and where the residual ecosystem-maturity costs (Section~\ref{sec:discussion_tradeoff}) fall on workloads small enough to absorb them. As \acs{WASI}~P2 capability coverage broadens and \acs{TEE}-rooted attestation matures (Section~\ref{sec:future_work_tee}), the boundary between the two tiers is likely to migrate further toward \acs{Wasm}.

\section{Threats to Validity}
\label{sec:threats_to_validity}

Several design choices and environmental constraints limit the generalisability of the results reported in this thesis.

\textbf{Single-node cluster.} All four primary variants run on a single 4-vCPU Hetzner Cloud \acs{VM} (ccx23) sharing the same kernel, network stack, and physical \acs{CPU} package. In a production multi-node cluster, scheduling, inter-node networking latency, and \acs{NUMA} topology would introduce additional variance not captured here. The results therefore characterise single-pod, co-located performance rather than at-scale distributed behaviour.

\textbf{Noisy-neighbour effects.} Although each benchmark run measures only one variant at a time, the load generator (k6) and the observability stack (Prometheus, Grafana) share the same host as the \acs{SUT}. \acs{CPU} and memory pressure from these background processes may inflate latency measurements, particularly for variants where baseline system load represents a proportionally larger share of available resources.

\textbf{Workload coverage.} Chapter~\ref{chap:evaluation} reports measured results for two stateless single-handler \acs{HTTP} workloads: the \acs{CPU}-bound prime sieve and the memory-bandwidth benchmark (heap allocation followed by a SHA-256 hash over the buffer). Both are short-lived request handlers that exercise Spin's \texttt{wasi:http/incoming-handler} dispatch path and the corresponding Docker entrypoint. Workloads dominated by network I/O (long-lived database connections, upstream \acs{HTTP} fan-out), filesystem I/O (file uploads, log writers), or long-lived state (WebSocket sessions, stateful sagas) interact differently with both the \acs{WASI}~P2 capability surface and the Wasmtime instance lifecycle, and are not exercised here. The Volta Monte Carlo \acs{VaR} engine described in Section~\ref{sec:workload_design} as a motivating example for the comparison has not been ported to the SpinKube variants and is left for future work (Section~\ref{sec:future_work_workloads}).

\textbf{Thread concurrency model.} The primary benchmark runs with resource-fairness constraints: \texttt{GOMAXPROCS=1} for docker-golang, \texttt{TOKIO\_WORKER\_THREADS=1} for docker-rust, and SpinApp \texttt{spec.replicas:~1} for the Spin variants (each \acs{WASI}~P1/P2 component is itself single-threaded per Wasmtime instance). This single-thread constraint ensures that the comparison isolates runtime overhead rather than concurrency model differences. A supplementary scaling experiment (Section~\ref{sec:eval_performance}) removes these constraints (GOMAXPROCS=4, TOKIO\_WORKER\_THREADS=4, SpinApp \texttt{spec.replicas:~4}) to measure how effectively each variant exploits the available 4-vCPU environment of the Hetzner ccx23 host.

\textbf{JIT-only compilation.} The Spin \acs{Wasm} variants use Wasmtime's default \acs{JIT} (Cranelift) compilation path. \acs{AOT} pre-compilation via \texttt{wasmtime compile} narrows the performance gap with native code; the results reported here therefore represent a conservative lower bound on attainable Wasmtime throughput. The trade-off is that \acs{JIT} preserves binary portability across architectures, which is the deployment model evaluated in this study.

\section{Future Work}
\label{sec:future_work}

This thesis evaluated the four-variant SpinKube/Wasmtime versus Docker matrix on a single-node Kubernetes cluster, under a deliberately narrow set of workloads, and using the Wasm runtime's default \acs{JIT} compilation path. Each of these scoping decisions opens a research direction that subsequent work could pursue. The strongest of those directions, however, concerns an area outside the scope of this study entirely: the intersection of \acs{Wasm} runtimes and hardware-enforced Confidential Computing. The remainder of this section describes that direction at length and then sketches three further extensions implied by the limitations enumerated in Section~\ref{sec:threats_to_validity}.

\subsection{WebAssembly inside Trusted Execution Environments}
\label{sec:future_work_tee}

The isolation primitive evaluated throughout this thesis is software-based: Wasm modules are confined to their linear-memory region via \acs{SFI}, and host resources are accessed only through the \acs{POLA}-driven capability surface of \acs{WASI}. A complementary primitive---hardware-enforced confidential execution via Trusted Execution Environments (\acs{TEE}s) such as Intel Software Guard Extensions (\acs{SGX}), Intel Trust Domain Extensions (\acs{TDX}), AMD Secure Encrypted Virtualization (\acs{SEV}-SNP), and ARM TrustZone---was deliberately out of scope but represents one of the most actively researched directions for the Wasm ecosystem. Confidential Computing protects code and data \emph{at runtime} from a privileged-but-untrusted host (a compromised hypervisor, a curious cloud operator, or a malicious co-tenant), a threat model the \acs{SFI} sandbox alone does not address. Combining the two is not redundant but stacked: \acs{SFI} bounds what a faulty Wasm module can reach inside its sandbox, and the surrounding \acs{TEE} bounds what the host can observe about that sandbox.

The structural fit between Wasm and \acs{TEE}s is unusually good. A Wasm runtime such as Wasmtime, WasmEdge, or \acs{WAMR} is roughly an order of magnitude smaller than a general-purpose \acs{OS} userland, so running the runtime plus a Wasm component inside an enclave keeps the Trusted Computing Base (\acs{TCB}) small---a property that matters because \acs{TEE} attestation must vouch for every byte that executes inside the enclave. The runtime's language-agnostic \acs{ABI} lets the same enclave image serve handlers written in Rust, Go, C, or any other Wasm-targeting language, removing the per-language enclave-porting cost that has historically constrained \acs{SGX}-only or TrustZone-only stacks. Finally, the deterministic execution semantics of Wasm align with the reproducible-build requirements of remote attestation: the same \texttt{.wasm} artifact produces the same enclave measurement on any platform, which simplifies attestation policies for multi-architecture deployments.

Existing research has demonstrated trusted Wasm runtimes on several hardware substrates. \textcite{menetrey2021twine} showed that a Wasmtime-derived runtime can execute inside an Intel \acs{SGX} enclave with manageable overhead, and the same group's follow-up~\cite{menetrey2022watz} ported the model to ARM TrustZone with remote-attestation support. \textcite{goltzsche2019acctee} earlier explored trusted resource accounting via a Wasm-in-\acs{SGX} sandbox. The Enarx project~\cite{enarx2024}, hosted under the Confidential Computing Consortium, abstracts over the underlying \acs{TEE} so that the same Wasm workload can target Intel \acs{SGX}, Intel \acs{TDX}, or AMD \acs{SEV}-SNP through a common runtime \acs{API}. At the Kubernetes layer, the Confidential Containers project~\cite{cncf2024coco} extends the Kata Containers runtime to launch pods inside confidential virtual machines, providing a deployment substrate that the SpinKube operator model evaluated in this thesis could plausibly target without a redesign of its \acs{CRD} interface.

Three research questions follow directly from the experimental setup developed in Chapter~\ref{chap:evaluation}. First, what is the throughput-and-latency cost of running the SpinKube/Wasmtime stack inside an \acs{SGX}, \acs{SEV}-SNP, or \acs{TDX} confidential virtual machine, relative to the limited-mode and unlimited-mode baselines reported there? The per-instruction \acs{SFI} bounds-checking tax measured in this thesis composes additively---or, in the worst case for memory-bound workloads, multiplicatively---with the enclave-page-cache and memory-encryption overheads inherent to \acs{TEE}s, and the combined cost is not yet well characterised for Spin-style \acs{HTTP} request-handler workloads. Second, how does cold-start latency change once an attestation flow (enclave measurement, quote generation, verification against an attestation service) is added to the SpinOperator's reconciliation loop, and can the small-\acs{OCI}-artifact advantage observed in Figure~\ref{fig:image_size_limited} be preserved when the artifact must additionally carry an enclave manifest? Third, does the \acs{WASI}~P2 capability model (\texttt{wasi:http}, \texttt{wasi:io}, \texttt{wasi:filesystem}) compose cleanly with attestation-rooted secret provisioning, or do new \acs{WIT} interfaces need to be designed for confidential serverless? Answering these would shift the SpinKube/Wasm comparison from a software-isolation study into a confidential-cloud-computing one---a setting in which Wasm's small-\acs{TCB} advantage is no longer a footnote but the central evaluation axis.

\subsection{Multi-node cluster deployment}
\label{sec:future_work_multinode}

The benchmark cluster used throughout this study runs upstream Kubernetes 1.34 on a single Hetzner ccx23 host (4 vCPU, 16\,GB \acs{RAM}). Section~\ref{sec:threats_to_validity} flags this as the most important limit on the external validity of the results: scheduling decisions, inter-node networking latency, and NUMA topology are absent from the measurement environment. Future work would re-run the same four-variant matrix on a multi-node cluster---ideally three to five worker nodes drawn from the same instance family so that per-node hardware variance is bounded---and measure how cross-node \texttt{kube-proxy} load-balancing interacts with the \acs{WASI}~P2 event-loop dispatch model under \texttt{spec.replicas:~N}. Of particular interest is whether the mid-test throughput dips observed in the wasm-rust per-second time series of Chapter~\ref{chap:evaluation} smooth out when traffic is spread across pods scheduled on different hosts, or whether they persist as a per-instance characteristic of Spin's request handler.

A multi-node setup additionally permits relocating the k6 load generator off the system-under-test node, eliminating the noisy-neighbour effect that the single-host environment cannot avoid, and would allow registry-side pull cost to be measured separately from runtime initialisation cost for both Docker and Spin artifacts.

\subsection{AOT compilation and alternative Wasm runtimes}
\label{sec:future_work_aot}

All measurements in this thesis use Wasmtime in its default \acs{JIT} (Cranelift) compilation mode, which trades steady-state throughput for fast startup. Wasmtime additionally supports \acs{AOT} pre-compilation via the \texttt{wasmtime compile} command, which removes the first-instantiation Cranelift pass from the warm-start critical path and is expected to narrow the throughput gap with native code---Section~\ref{sec:threats_to_validity} already notes that the results presented here are therefore a conservative lower bound on attainable Wasmtime performance. A natural extension is to re-run the same four-variant comparison under \acs{AOT} for Wasmtime, and additionally under WasmEdge and \acs{WAMR}, both of which are supported by parallel containerd shims usable in place of \texttt{containerd-shim-spin-v2}. Wasmtime's newer Winch baseline compiler is also worth measuring as an intermediate operating point that trades steady-state throughput for even faster cold-start than Cranelift.

\subsection{Broader workload spectrum}
\label{sec:future_work_workloads}

The two benchmarks measured here---a \acs{CPU}-bound prime sieve and a memory-bandwidth workload combining heap allocation with SHA-256 hashing---are stateless single-handler \acs{HTTP} services. Workloads dominated by network I/O (database queries, upstream \acs{HTTP} calls), filesystem I/O (file uploads, log writers), or long-lived state (WebSocket sessions, stateful sagas) interact differently with both the \acs{WASI}~P2 capability model and the Wasmtime instance lifecycle, and several of those interactions are not exercised in the current study. In particular, \acs{WASI}~P2's \texttt{wasi:sockets} and \texttt{wasi:filesystem} interfaces are barely touched here because Spin's \acs{HTTP} trigger short-circuits both. Future work would add a database-backed workload (for example, a Postgres-backed REST handler exercising \texttt{wasi:sockets}) and a filesystem-heavy workload to characterise these interfaces under load, alongside the Volta Monte Carlo \acs{VaR} engine mentioned in Chapter~\ref{chap:methodology} but not yet benchmarked on the SpinKube variants.
