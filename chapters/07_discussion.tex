\section{The WASI P1 to P2 Transition}
\label{sec:wasi_p1_p2_transition}

The transition from \acs{WASI}~P1 (WasmEdge/\acs{LLVM}) to \acs{WASI}~P2 (SpinKube/Wasmtime/Cranelift) eliminates the single-threaded I/O bottleneck at the architectural level. The \acs{WASI}~P1 variants documented in Appendix~\ref{app:wasmedge_p1} were constrained by a blocking single-threaded \texttt{accept()} loop, yielding 24\,\acs{RPS} for wasm-rust with a 67\% failure rate under 50 concurrent virtual users---a 20$\times$ throughput gap relative to docker-rust (479\,\acs{RPS}, 0\% failures).

SpinKube's request-handler model dispatches each incoming request to a fresh Wasmtime component instance. Under \texttt{max\_instances=4}, the host can execute four concurrent sieve computations simultaneously---a qualitatively different execution model from the P1 accept loop. The pending benchmark results (Section~\ref{sec:eval_performance}) will determine whether this architectural change closes the throughput gap with Docker under the 50-VU load profile, or whether other factors (Cranelift \acs{JIT} overhead, SpinOperator dispatch latency, component instantiation cost) impose a different ceiling.

An acknowledged limitation is that this transition introduces two simultaneous confounding variables: the \acs{WASI} version change (P1~$\to$~P2) and the \acs{JIT} backend change (WasmEdge/\acs{LLVM}~$\to$~Wasmtime/Cranelift). Disentangling these two effects would require a runtime that supports \acs{WASI}~P2 with the \acs{WasmEdge}/\acs{LLVM} backend---which does not exist at production readiness at time of writing.

\section{Threats to Validity}
\label{sec:threats_to_validity}

Several design choices and environmental constraints limit the generalisability of the results reported in this thesis.

\textbf{Single-node cluster.} All four primary variants run on a single two-vCPU Hetzner Cloud \acs{VM} sharing the same kernel, network stack, and physical \acs{CPU}. In a production multi-node cluster, scheduling, inter-node networking latency, and \acs{NUMA} topology would introduce additional variance not captured here. The results therefore characterise single-pod, co-located performance rather than at-scale distributed behaviour.

\textbf{Noisy-neighbour effects.} Although each benchmark run measures only one variant at a time, the load generator (k6) and the observability stack (Prometheus, Grafana) share the same host as the \acs{SUT}. \acs{CPU} and memory pressure from these background processes may inflate latency measurements, particularly for variants where baseline system load represents a proportionally larger share of available resources.

\textbf{Single workload type (compute-bound only for primary results).} Quantitative results are currently available only for the \acs{CPU}-bound prime sieve benchmark. The memory-bandwidth workload (implemented in \texttt{benchmarks/02-memory-bandwidth/}) and the Volta Monte Carlo \acs{VaR} engine described in Section~\ref{sec:workload_design} have not yet been benchmarked on the SpinKube variants. Workloads dominated by file I/O, database access, or inter-service communication may exhibit a substantially different performance profile.

\textbf{Thread concurrency model.} The primary benchmark runs with resource-fairness constraints: \texttt{GOMAXPROCS=1} for docker-golang, \texttt{TOKIO\_WORKER\_THREADS=1} for docker-rust, and \texttt{max\_instances=1} for Spin variants. This single-thread constraint ensures that the comparison isolates runtime overhead rather than concurrency model differences. A supplementary scaling experiment (Section~\ref{sec:eval_performance}) removes these constraints (GOMAXPROCS=2, TOKIO\_WORKER\_THREADS=2, Spin max\_instances=4) to measure how effectively each variant exploits the available 2-vCPU environment.

\textbf{JIT-only compilation.} The Spin \acs{Wasm} variants use Wasmtime's default \acs{JIT} (Cranelift) compilation path. \acs{AOT} pre-compilation via \texttt{wasmtime compile} narrows the performance gap with native code; the results reported here therefore represent a conservative lower bound on attainable Wasmtime throughput. The trade-off is that \acs{JIT} preserves binary portability across architectures, which is the deployment model evaluated in this study. Similarly, the optional \acs{WasmEdge} variants in Appendix~\ref{app:wasmedge_p1} use \acs{WasmEdge}'s \acs{JIT} path; \acs{AOT} pre-compilation via \texttt{wasmedgec} would eliminate the \acs{LLVM} startup cost and the outlier warm-start times observed there.

\textbf{Confounding variable: WASI version and JIT backend.} As noted in Section~\ref{sec:wasi_p1_p2_transition}, the comparison between the primary SpinKube variants and the optional \acs{WasmEdge} variants conflates two changes simultaneously. This is an inherent limitation of the current \acs{Wasm} ecosystem: no mature \acs{WASI}~P2 \acs{HTTP} framework exists for \acs{WasmEdge}, and no mature \acs{WASI}~P1 long-running-server framework exists for Wasmtime. The primary research question (Docker vs.\ \acs{Wasm} for microservices) is answered using the best available production-ready toolchain for each paradigm.
