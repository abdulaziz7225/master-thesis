\chapter{Conclusion}
\label{chap:conclusion}

This thesis set out to answer whether \acs{Wasm}/SpinKube is a viable alternative to Docker for high-density \acs{HTTP} microservices in Kubernetes, comparing four variants across five metrics: \acs{OCI} artifact size, startup latency, runtime performance under load, memory footprint, and developer experience.

The primary 4-variant experiment (wasm-rust, wasm-tinygo, docker-rust, docker-golang) uses SpinKube/Wasmtime --- configured for \acs{WASI}~P2 components (wasm-rust) and the legacy Spin HTTP interface (wasm-tinygo, \acs{WASI}~P1 via the Spin Go \acs{SDK}'s \acs{CGo} bridge) --- as the \acs{Wasm} execution environment. Quantitative benchmark measurements are pending cluster execution (Section~\ref{sec:eval_performance}). The developer experience assessment is complete (Section~\ref{sec:eval_dx}) and indicates that SpinKube provides a low-friction Wasm development experience: standard \texttt{net/http} types work with TinyGo via the Spin Go SDK, and the \texttt{spin-sdk} for Rust provides a standards-compliant component model handler without custom networking code.

The central open question---whether SpinKube's request-handler model achieves comparable throughput to Docker variants under concurrent load---will be answered by the pending benchmark execution.

The memory-bandwidth benchmark (02-memory-bandwidth, implemented in \texttt{benchmarks/02-memory-bandwidth/}) extends the evaluation beyond \acs{CPU}-bound computation to test memory-allocation patterns and filesystem access behaviour under \acs{WASI}~P2. The worker-thread scaling experiment (Section~\ref{sec:eval_performance}) will quantify how effectively each variant exploits available \acs{CPU} parallelism when resource constraints are relaxed.

\textit{This chapter will be expanded with quantitative conclusions once the SpinKube benchmark measurements are complete.}
