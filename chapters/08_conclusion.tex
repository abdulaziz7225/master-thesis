\chapter{Conclusion}
\label{chap:conclusion}

This thesis compared a SpinKube/Wasmtime stack to a Docker / \texttt{runc} baseline across four variants---\texttt{wasm-rust}, \texttt{wasm-tinygo}, \texttt{docker-rust}, and \texttt{docker-golang}---under two stateless \acs{HTTP} workloads (a \acs{CPU}-bound prime sieve and a memory-bandwidth benchmark combining heap allocation with SHA-256 hashing) on a single-node Kubernetes 1.34 cluster running on a 4-vCPU Hetzner ccx23 host. Each variant was evaluated on five metrics: \acs{OCI} artifact size, startup latency, sustained throughput and end-to-end latency under load, memory and \acs{CPU} footprint, and developer experience. With both benchmarks measured under the limited (single worker thread / single replica) and unlimited (\texttt{GOMAXPROCS}=\texttt{TOKIO\_WORKER\_THREADS}=4, \texttt{SpinApp~spec.replicas:~4}) configurations, the four research questions posed in Chapter~\ref{chap:introduction} can now be answered against measured data rather than against projection.

\textbf{RQ1: memory footprint and \acs{OCI} artifact size.} The artifact-size axis strongly favours the \acs{Wasm} stack: the \texttt{wasm-rust} artifact (0.20\,MB) is approximately 30$\times$ smaller than \texttt{docker-golang} (5.99\,MB) and ~9$\times$ smaller than \texttt{docker-rust} (1.85\,MB), with \texttt{wasm-tinygo} (0.48\,MB across all four workloads after the TinyGo \texttt{-no-debug} build flag detailed in Chapter~\ref{chap:implementation}) sitting much closer to wasm-rust than to the Docker variants, putting both \acs{Wasm} variants approximately an order of magnitude below the smallest Docker artefact (Section~\ref{sec:eval_artifact_size}). Resident-memory footprint, however, inverts the ranking: the \acs{Wasm} variants carry roughly 20\,MiB of \acs{RSS} for Wasmtime's \acs{JIT} compilation context and the pre-allocated linear-memory region, while \texttt{docker-rust}---which ships only the stripped Tokio executable on a \texttt{scratch} base---holds just 1--3\,MiB (Section~\ref{sec:eval_resources}). The trade-off is therefore ``\acs{Wasm} wins on-disk density, Docker wins resident-memory packing''; capacity planning on a memory-constrained host favours the minimal-scratch Docker variant, while a disk- or pull-bandwidth-constrained edge node favours the Spin artifacts.

\textbf{RQ2: cold- and warm-start latency.} Three of the four variants---both \acs{Wasm} components and \texttt{docker-rust}---return their first \acs{HTTP}~200 within a ~21--35\,ms band regardless of whether the image is cached on the node, with sub-4\,ms warm-start standard deviation (Section~\ref{sec:eval_startup}). The cold-start argument that prior literature framed as a general ``Docker versus \acs{Wasm}'' phenomenon~\cite{long2023wasm, wiegratz2024k8swasm} therefore manifests only against the heaviest container in this study: \texttt{docker-golang} takes ~3.7--4.8\,s cold (depending on the workload) and ~3.9--5.9\,s warm, an overhead that persists when the image is already on-node and is therefore rooted in the container's entrypoint and runtime bootstrap rather than in the pull path. For scale-to-zero serverless dispatch against minimal-base Docker images, the choice between SpinKube/\acs{Wasm} and a \texttt{scratch}-based container is effectively a tie at the first-response milestone.

\textbf{RQ3: throughput and end-to-end latency.} Under \acs{WASI}~P2 with Spin's event-loop dispatch in limited mode, the four-variant spread is 2.58$\times$ on the prime sieve and 2.28$\times$ on memory-bandwidth---much tighter than the ~10$\times$ gap reported by \textcite{sondell2024performance} under \acs{WASI}~P1 single-instance dispatch. \texttt{wasm-rust} trails \texttt{docker-golang} by ~21\% on prime-sieve throughput in limited mode, with comparable p50 latency (15.1\,ms versus 12.1\,ms) but a wider p99 tail (34.2\,ms versus 21.8\,ms) attributable to Wasmtime's \acs{JIT} compilation context; the queueing-induced tail blow-up the same prior work observed under \acs{WASI}~P1 does not appear as a catastrophic outlier in either Wasm variant (Section~\ref{sec:eval_performance}). Unlimited mode (the 4-vCPU environment with four worker threads / four \texttt{SpinApp} replicas, \texttt{limits.cpu} raised to 4000\,m) helps the Docker variants more than \texttt{wasm-rust}, whose \acs{WASI}~P2 event-loop already saturates a single pod's \acs{CPU} budget via \texttt{wasi:io/poll} suspension points; Docker keeps a consistent lead in unlimited mode (~24\% on \acs{CPU}-bound throughput, ~30\% on memory-bandwidth throughput between docker-golang and wasm-rust). The residual deficit on both workloads is concentrated in the \texttt{wasm-tinygo} variant, where the bundled TinyGo runtime dominates per-request overhead.

\textbf{RQ4: developer experience and ecosystem integration.} All four variants sit at \emph{Low} dependency-compatibility friction (Section~\ref{sec:eval_dx}): the Spin Go \acs{SDK}'s \texttt{spinhttp.Handle()} and the Rust \texttt{spin-sdk} crate let standard \texttt{net/http} handlers and standard Rust async networking code compile and run unmodified, without the proprietary socket workarounds older \acs{WASI}~P1 \acs{SDK}s required. Toolchain-setup friction is \emph{Low-Medium}: \texttt{wasm-rust} adds one \texttt{cargo install cargo-component} step beyond a stock Rust install and the \texttt{wasm32-wasip2} target via \texttt{rustup}; \texttt{wasm-tinygo} requires TinyGo 0.40.0 as a \texttt{.tar.gz} release plus the \texttt{-target=wasip1} flag because TinyGo's \texttt{wasip2} target cannot currently export \texttt{wasi:http/incoming-handler}. Kubernetes integration adds the \texttt{wasmtime-spin} \texttt{RuntimeClass} and the SpinOperator Helm chart but is otherwise a standard \texttt{kubectl apply} workflow against the \texttt{SpinApp} \acs{CRD}. The remaining friction is debugging: \texttt{kubectl exec} does not work on \acs{Wasm} pods, and no native debugger can attach to a running Wasmtime instance from outside the sandbox---a constraint inherent to the \acs{WASI} execution model that the ecosystem is expected to mitigate, not eliminate, as second-generation tooling matures.

\textbf{Outlook.} The strongest follow-on direction is the intersection of \acs{Wasm} runtimes and hardware-enforced confidential computing developed in Section~\ref{sec:future_work_tee}: the small-\acs{TCB} property that makes the SpinKube/Wasmtime stack attractive in pure software-isolation terms is the same property that makes it a natural fit for \acs{TEE} substrates such as Intel \acs{SGX}/\acs{TDX}, AMD \acs{SEV}-SNP, and the Confidential Containers project---a setting in which \acs{Wasm}'s small-\acs{TCB} advantage shifts from a footnote into the central evaluation axis. Two further extensions, deferred here by the scope choices documented in Chapter~\ref{chap:methodology}, sit one step behind: a multi-node validation of the same four-variant matrix on a cross-host Kubernetes cluster (Section~\ref{sec:future_work_multinode}), and a re-measurement of the \acs{Wasm} variants under Wasmtime \acs{AOT} compilation, Wasmtime's Winch baseline, and the parallel WasmEdge and \acs{WAMR} runtimes (Section~\ref{sec:future_work_aot}). Taken together, the headline contribution of this thesis is empirical evidence that \acs{WASI}~P2 with Spin's event-loop dispatch closes most of the previously observed \acs{Wasm}-versus-native gap on stateless \acs{HTTP} workloads---making ecosystem maturity, rather than runtime efficiency, the binding constraint on \acs{Wasm} adoption inside Kubernetes today.
