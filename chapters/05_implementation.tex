\chapter{Implementation}
\label{chap:implementation}

This chapter describes the end-to-end implementation of the benchmark environment: the rationale for using a dedicated cloud \acs{VM}, the infrastructure provisioning process, the design of the reference workload, all four service implementations, and the \acs{K8s} deployment configuration.

\section{Why a Dedicated Cloud Virtual Machine}
\label{sec:infra_rationale}

The primary goal of the experimental infrastructure is measurement \textit{isolation}: ensuring that observed performance differences between variants reflect genuine runtime and language characteristics, not environmental noise. Three alternative approaches were evaluated before settling on a dedicated Hetzner Cloud \acs{VM}:

\begin{itemize}
    \item \textbf{Local Minikube:} Runs a \acs{K8s} cluster inside a \acs{VM} on the developer's laptop. Background processes (browser, IDE, system updates) compete for \acs{CPU} and memory, making benchmark results unreproducible across sessions. Additionally, consumer laptop \acs{CPU} governors apply dynamic frequency scaling under load, introducing measurement variance.
    \item \textbf{k3d (K3s in Docker):} Runs a K3s cluster inside Docker containers on the local machine. This introduces multiple hypervisor/container nesting layers---host \acs{OS} $\to$ Docker $\to$ K3s $\to$ containerd $\to$ \acs{Wasm} runtime---that obscure the runtime overhead being measured and complicate the registration of the SpinKube containerd shim.
    \item \textbf{Managed Cloud \acs{K8s} (EKS, GKE, AKS):} Managed \acs{K8s} offerings do not support custom \acs{OCI} runtimes or \texttt{RuntimeClass} with non-standard shims out of the box. Adding SpinKube (\texttt{containerd-shim-spin-v2}) support requires custom node groups or operator-managed DaemonSets, adding abstraction layers that complicate fair comparison.
\end{itemize}

A dedicated Hetzner Cloud \acs{VM} provides a single-purpose environment with no competing workloads, full control over kernel configuration and containerd setup, and complete reproducibility via \ac{IaC}~\cite{terraform2024hashicorp}; the provisioning Terraform modules and cloud-init bootstrap scripts are published as the \texttt{thesis-infra-setup} repository~\cite{musaev2026thesisinfra}. The Hetzner ccx-series \acs{CPU} type is a dedicated-vCPU instance family; occasional noisy-neighbour effects from co-located tenants on the underlying host may still introduce outliers in absolute metric values. This is mitigated by repeating measurements across multiple runs and reporting means and standard deviations.

\section{Infrastructure Setup}
\label{sec:infra_setup}

\subsection{Hardware and Kubernetes Distribution}

The benchmark cluster runs on a Hetzner Cloud ccx23 instance~\cite{hetzner2024cloud}. Hetzner Online GmbH is a German cloud and hosting provider offering cost-efficient dedicated and shared virtual machines in European data centers; the ccx23 is a dedicated-\acs{CPU} instance type with four \acs{AMD} EPYC vCPUs, 16\,GB \acs{RAM}, 160\,GB NVMe \acs{SSD}, running Ubuntu~24.04~LTS in the Nuremberg~(nbg1) datacenter. The entire server provisioning is defined in Terraform~\cite{terraform2024hashicorp}---an open-source \acl{IaC} tool that declaratively manages cloud resources---and executed with a single \texttt{make up} command.

Upstream Kubernetes v1.34, deployed via \texttt{kubeadm}, is installed as the \acs{K8s} distribution. \texttt{kubeadm} is the reference installer in the official Kubernetes documentation and is the foundation that managed services such as \acs{AWS} \acs{EKS}, Google \acs{GKE}, and Azure \acs{AKS} run underneath; using it removes distribution-specific confounds from the runtime comparison. The ccx23 sizing provides ample headroom above the combined footprint of the kubeadm control plane (apiserver, etcd, controller-manager, scheduler, kube-proxy), \texttt{cert-manager}, the SpinOperator, the kube-prometheus-stack observability stack, and the benchmark workload pods. Services are exposed via NodePort directly without an ingress controller, to avoid introducing an irrelevant processing layer between the load generator and the measured services. containerd~2.x is used as the \ac{CRI}---the standardized interface through which the kubelet communicates with the container runtime to manage pod lifecycles---and Flannel provides the pod-network \acs{CNI}.

\subsection{The SpinKube Runtime Chain}

Running \acs{Wasm} pods alongside standard \acs{OCI} pods requires configuring containerd to route \acs{Wasm} workloads through a different \acs{OCI} runtime. The full SpinKube chain is:

\begin{center}
\texttt{kubelet} $\to$ \texttt{containerd} $\to$ \texttt{containerd-shim-spin-v2} $\to$ \textbf{Wasmtime/Cranelift} $\to$ \texttt{.wasm component}
\end{center}

The key components in this chain are:

\begin{itemize}
    \item \textbf{containerd-shim-spin-v2~v0.17.0:} A containerd shim that implements the containerd shim v2 protocol and embeds Fermyon Spin (which embeds Wasmtime/Cranelift) internally. It does \textit{not} use crun or runc; the shim is the direct process host for the \acs{Wasm} component. Installed from the SpinKube GitHub release as a static binary at \texttt{/usr/local/bin/containerd-shim-spin-v2}.
    \item \textbf{containerd plugin entry:} The containerd configuration registers a \texttt{spin} runtime plugin with \texttt{runtime\_type = 'io.containerd.spin.v2'}. This is always active; no pod annotations are required.
    \item \textbf{SpinOperator (v0.6.1):} A Kubernetes operator (CNCF Sandbox) that watches \texttt{SpinApp} \acs{CRD} resources and creates managed \texttt{Deployments} with \texttt{runtimeClassName: wasmtime-spin}. cert-manager~v1.16.3 is a prerequisite for the operator's admission webhook.
    \item \textbf{Wasmtime/Cranelift:} The \acs{JIT} engine embedded inside Spin. All \acs{WASI}~P2 component execution uses Wasmtime with the Cranelift \acs{JIT} backend.
\end{itemize}

\subsection{Observability Stack}

Observability refers to the ability to infer the internal state of a system from its external outputs---primarily metrics, logs, and traces. In this experimental context, observability is required to collect the quantitative performance metrics defined in Chapter~\ref{chap:methodology} (memory, \acs{CPU}, request latency, and throughput) from all six variants simultaneously and under identical conditions.

The \texttt{kube-prometheus-stack} Helm chart is deployed into the \texttt{observability} namespace, providing Prometheus~\cite{prometheus2024cncf} (NodePort~32090, 5\,s scrape interval, 7-day retention, 10\,Gi \acs{PVC}) and Grafana (NodePort~32000). A 5-second scrape interval was chosen to capture sub-second metric resolution during the 60-second k6 load window. Node Exporter provides host-level \acs{CPU} and memory metrics; the \texttt{cAdvisor} integration in containerd exposes per-container \texttt{container\_memory\_rss} and \texttt{container\_cpu\_usage\_seconds\_total} metrics.

\subsection{Infrastructure as Code}

The entire environment is described declaratively:

\begin{itemize}
    \item \textbf{Terraform} provisions the Hetzner Cloud firewall (restricting \acs{SSH} and \acs{K8s} \acs{API} access to the operator's \acs{IP}) and the ccx23 \acs{VM}.
    \item \textbf{cloud-init} installs containerd~2.x, \texttt{kubeadm}/\texttt{kubelet}/\texttt{kubectl} (v1.34), runs \texttt{kubeadm init}, installs the Flannel \acs{CNI} and \texttt{local-path-provisioner}, untaints the control-plane node, and installs \texttt{containerd-shim-spin-v2}. The complete environment, from bare cloud \acs{VM} to a functioning SpinKube-enabled \acs{K8s} cluster with observability, is bootstrapped with \texttt{make up \&\& make configure \&\& make deploy}.
\end{itemize}

\section{Reference Workload: Sieve of Eratosthenes}
\label{sec:reference_workload}

The Sieve of Eratosthenes is a classical algorithm for finding all prime numbers up to a given limit $N$. The implementation marks composite numbers by iterating through multiples of each discovered prime, completing in $O(N \log \log N)$ time with $O(N)$ space. All six variants implement the identical algorithmic logic; the only differences are the \acs{HTTP} framework and I/O model.

The \acs{HTTP} \acs{API} is:
\begin{verbatim}
GET /prime?limit=N&no_list=1
\end{verbatim}
where \texttt{limit} is capped at 10,000,000 across all variants. The \acs{JSON} response contains the fields \texttt{runtime}, \texttt{limit}, \texttt{count}, and \texttt{elapsed\_us}. The \texttt{elapsed\_us} field measures only the sieve computation, not network or serialization time. The \texttt{no\_list} flag suppresses the array of prime numbers, ensuring that \acs{JSON} encoding time does not confound throughput measurements.

Each variant also exposes \texttt{GET /health} returning \acs{HTTP}~200, used for \acs{K8s} liveness and readiness probes.

\section{Docker/Golang Implementation}
\label{sec:impl_docker_golang}

The docker-golang service uses Go~1.26 and the \texttt{net/http} standard library. The server is started with \texttt{http.ListenAndServe(":8080", mux)}, which creates one goroutine per accepted connection. Go's M:N scheduler multiplexes goroutines onto \acs{OS} threads, enabling concurrent request handling without explicit thread management. The sieve computation and \acs{JSON} marshaling use only standard library packages (\texttt{encoding/json}), resulting in zero external dependencies.

The Docker image uses a two-stage build: a \texttt{golang:1.26-alpine} builder stage compiles a fully static binary with \texttt{CGO\_ENABLED=0 GOOS=linux}, and a \texttt{scratch} final stage contains only the binary. The resulting image is \textbf{6.00\,MB}, the largest of the Docker/\acs{WASI}~P1 variants due to Go's compiled-in runtime metadata (goroutine scheduler, garbage collector, standard library \acs{DWARF} symbols).

\section{Docker/Rust Implementation}
\label{sec:impl_docker_rust}

The docker-rust service uses Rust~1.94 with the axum~0.8 web framework running on the Tokio async runtime. The \texttt{\#[tokio::main]} macro spawns a multi-threaded executor whose thread count equals the number of available \acs{CPU} cores. Axum's async handler model allows all 50 concurrent k6 \acp{VU} to be processed in parallel, with each handler awaiting the sieve computation in its own async task.

The Docker image uses a two-stage build: a \texttt{rust:1.94-slim} builder stage with \texttt{cargo build --release} (link-time optimisation enabled, \texttt{codegen-units=1}, \texttt{opt-level=3}, binary stripped), and a \texttt{scratch} final stage. The resulting image is \textbf{2.08\,MB}---3$\times$ smaller than docker-golang, reflecting Rust's lack of a garbage collector and the absence of any bundled runtime metadata.

\section{SpinKube/Rust Implementation}
\label{sec:impl_spin_rust}

\subsection{HTTP Handler via spin-sdk}

The wasm-rust variant uses \texttt{spin-sdk~=~"5.2.0"}, the official Spin \acs{SDK} for Rust \acs{WASI}~P2 components. The \texttt{\#[http\_component]} procedural macro generates the \acs{WASI}~P2 \texttt{wasi:http/incoming-handler} export automatically:

\begin{verbatim}
use spin_sdk::http::{IncomingRequest, Response};
use spin_sdk::http_component;

#[http_component]
fn handle(req: IncomingRequest) -> Response {
    match req.path_with_query().as_deref() {
        Some(p) if p.starts_with("/prime") => sieve_handler(&req),
        Some("/health") => health_handler(),
        _ => Response::builder().status(404).body("not found").build(),
    }
}
\end{verbatim}

There is no \acs{TCP} socket management, no accept loop, and no custom \acs{HTTP} parsing. Spin's Wasmtime/Cranelift host handles all of that; the component receives a parsed \texttt{IncomingRequest} and returns a \texttt{Response}.

\subsection{Build and Packaging}

The component is built with \texttt{cargo component build --release} (from the \texttt{cargo-component} toolchain), which compiles to a \acs{WASI}~P2 component and runs \texttt{wasm-tools component link} to produce a self-contained \texttt{.wasm} file. The artifact is pushed to the registry as a Spin \acs{OCI} artifact---not a standard Docker image---using \texttt{spin registry push docker.io/abdulaziz7225/prime-sieve-wasm-rust:latest}. Spin \acs{OCI} artifacts use distinct media types (\texttt{application/vnd.fermyon.spin.manifest.v2+json}) that require \texttt{containerd-shim-spin-v2} to pull and execute correctly.

Concurrency is capped at the pod level: the limited-mode baseline runs the \texttt{SpinApp} with \texttt{spec.replicas:~1}, and each \acs{WASI}~P1/P2 component is architecturally single-threaded per Wasmtime instance, satisfying the resource-fairness requirement without any in-component setting. (Spin~2.x [\texttt{spin\_manifest\_version~=~2}] no longer accepts the legacy \texttt{max\_instances} field that earlier Spin 1.x versions exposed in \texttt{spin.toml}.) The compiled \texttt{.wasm} artifact is typically under 1\,MB stripped.

Source: \texttt{wasm/rust/01-prime-sieve/}

\section{SpinKube/TinyGo Implementation}
\label{sec:impl_spin_tinygo}

\subsection{HTTP Handler via Spin Go SDK}

The wasm-tinygo variant uses the official Spin \acs{SDK} for Go (\texttt{github.com/spinframework/spin-go-sdk/v2}). The \texttt{spinhttp.Handle()} function registers the application's \acs{HTTP} handler via a \acs{CGo} layer that exports \texttt{fermyon:spin/inbound-http}, the interface Spin/Wasmtime dispatches \acs{HTTP} requests through. The handler receives standard \texttt{net/http.ResponseWriter} and \texttt{*http.Request} arguments:

\begin{verbatim}
func init() {
    mux := http.NewServeMux()
    mux.HandleFunc("/prime",  sieveHandler)
    mux.HandleFunc("/health", healthHandler)
    spinhttp.Handle(func(w http.ResponseWriter, r *http.Request) {
        mux.ServeHTTP(w, r)
    })
}
func main() {}
\end{verbatim}

\textbf{No custom socket code is required.} No \texttt{//go:wasmimport} socket directives or custom \texttt{server.go} are needed. Note that \texttt{-target=wasip1} is used rather than \texttt{wasip2}: TinyGo's \texttt{wasip2} target hardwires the \texttt{wasi:cli/command} world and cannot export \texttt{wasi:http/incoming-handler}; the Spin Go \acs{SDK}'s \acs{CGo} layer provides the correct HTTP export instead. The handler logic is identical to the docker-golang handler, providing the closest possible Go-to-Go comparison.

\subsection{Build and Packaging}

The binary is compiled with:
\begin{verbatim}
tinygo build -target=wasip1 -gc=conservative -opt=2 -o app.wasm .
\end{verbatim}
The \texttt{-gc=conservative} flag is retained for stability. \texttt{-target=wasip1} is required: TinyGo's \texttt{wasip2} target hardwires \texttt{wasi:cli/command} and cannot export \texttt{wasi:http/incoming-handler}; the Spin Go \acs{SDK} exports \texttt{fermyon:spin/inbound-http} via its \acs{CGo} layer, which Spin accepts as an equivalent interface. The \texttt{.wasm} artifact is packaged as a Spin \acs{OCI} artifact using \texttt{spin registry push}. The limited-mode baseline runs the \texttt{SpinApp} with \texttt{spec.replicas:~1}; the \acs{WASI}~P1 component itself is single-threaded per Wasmtime instance, so no additional \texttt{spin.toml} concurrency setting is required (resource fairness).

Source: \texttt{wasm/tinygo/01-prime-sieve/}

\section{Kubernetes Deployment Configuration}
\label{sec:k8s_deployment}

All four primary variants are deployed into the \texttt{prime-sieve} namespace. The Docker variants each have a standard \texttt{Deployment} (1 replica) and a \texttt{Service} of type \texttt{NodePort}. The Spin variants use a \texttt{SpinApp} \acs{CRD} (managed by the SpinOperator) plus a \texttt{NodePort} \texttt{Service}.

\textbf{Docker variants} use standard \texttt{Deployment} manifests with no \texttt{runtimeClassName}; containerd routes these pods through the default \texttt{runc} path.

\textbf{Spin variants} are deployed via the \texttt{SpinApp} \acs{CRD}. The SpinOperator reads the \texttt{SpinApp} resource, creates a managed \texttt{Deployment}, and applies \texttt{runtimeClassName: wasmtime-spin} to its pods---routing them through \texttt{containerd-shim-spin-v2}, which embeds Spin and Wasmtime/Cranelift. Spin images must be pushed via \texttt{spin registry push} (not \texttt{docker push}), as the shim expects Spin-specific \acs{OCI} media types (\texttt{application/vnd.fermyon.spin.manifest.v2+json}). Concurrency in the limited mode is capped by running the SpinApp with \texttt{spec.replicas:~1}; each \acs{WASI}~P1/P2 component is architecturally single-threaded per instance. Scaling must be done via \texttt{kubectl patch spinapp} rather than \texttt{kubectl scale deployment}: the SpinOperator reconciles direct Deployment scaling back to the \texttt{SpinApp}'s \texttt{spec.replicas}.

\textbf{Resource fairness (supervisor requirement).} All four variants specify identical resource envelopes: \texttt{requests} of 250m \acs{CPU} and 64\,MiB memory, and \texttt{limits.memory} of 128\,MiB. The \texttt{limits.cpu} value is mode-dependent: 500m for the limited-mode comparison and 4000m for the unlimited-mode scaling experiment, raised so that cgroup CPU bandwidth control does not throttle the additional worker threads introduced in unlimited mode (see Section~\ref{sec:eval_performance}). To ensure a fair single-thread limited-mode comparison, \texttt{GOMAXPROCS=1} is set in the \texttt{docker-golang} manifest, \texttt{TOKIO\_WORKER\_THREADS=1} is set in the \texttt{docker-rust} manifest, and the Spin variants run with \texttt{SpinApp~spec.replicas:~1} so that each variant serves one request at a time.

Liveness and readiness probes execute \texttt{GET /health}. Docker variants use a 5-second initial delay; Spin variants rely on the SpinOperator's rollout health management via the \texttt{SpinApp} ready condition.
