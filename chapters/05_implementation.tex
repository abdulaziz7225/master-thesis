\chapter{Implementation}
\label{chap:implementation}

This chapter describes the end-to-end implementation of the benchmark environment: the rationale for using a dedicated cloud \acs{VM}, the infrastructure provisioning process, the design of the reference workload, all four service implementations, and the \acs{K8s} deployment configuration.

\section{Why a Dedicated Cloud Virtual Machine}
\label{sec:infra_rationale}

The primary goal of the experimental infrastructure is measurement \textit{isolation}: ensuring that observed performance differences between variants reflect genuine runtime and language characteristics, not environmental noise. Three alternative approaches were evaluated before settling on a dedicated Hetzner Cloud \acs{VM}:

\begin{itemize}
    \item \textbf{Local Minikube:} Runs a \acs{K8s} cluster inside a \acs{VM} on the developer's laptop. Background processes (browser, IDE, system updates) compete for \acs{CPU} and memory, making benchmark results unreproducible across sessions. Additionally, consumer laptop \acs{CPU} governors apply dynamic frequency scaling under load, introducing measurement variance.
    \item \textbf{k3d (K3s in Docker):} Runs a K3s cluster inside Docker containers on the local machine. This introduces multiple hypervisor/container nesting layers---host \acs{OS} $\to$ Docker $\to$ K3s $\to$ containerd $\to$ \acs{Wasm} runtime---that obscure the runtime overhead being measured and prevent the \acs{WasmEdge} containerd shim from registering correctly.
    \item \textbf{Managed Cloud \acs{K8s} (EKS, GKE, AKS):} Managed \acs{K8s} offerings do not support custom \acs{OCI} runtimes or \texttt{RuntimeClass} with non-standard shims out of the box. Adding \acs{WasmEdge} support requires custom node groups with operator-managed DaemonSets, adding abstraction layers that complicate fair comparison.
\end{itemize}

A dedicated Hetzner Cloud \acs{VM} provides a single-purpose environment with no competing workloads, full control over kernel configuration and containerd setup, and complete reproducibility via \ac{IaC}~\cite{terraform2024hashicorp}. The shared-hardware nature of the \acs{VM} (Hetzner ccx13 is a shared \acs{CPU} type) is acknowledged as a limitation: occasional noisy-neighbour effects from co-located tenants may introduce outliers in absolute metric values. This is mitigated by repeating measurements across multiple runs and reporting means and standard deviations.

\section{Infrastructure Setup}
\label{sec:infra_setup}

\subsection{Hardware and Kubernetes Distribution}

The benchmark cluster runs on a Hetzner Cloud ccx13 instance~\cite{hetzner2024cloud}. Hetzner Online GmbH is a German cloud and hosting provider offering cost-efficient dedicated and shared virtual machines in European data centers; the ccx13 is a shared-\acs{CPU} instance type with two dedicated \acs{AMD} EPYC vCPUs, 8\,GB \acs{RAM}, 80\,GB NVMe \acs{SSD}, running Ubuntu~24.04~LTS in the Nuremberg~(nbg1) datacenter. The entire server provisioning is defined in Terraform~\cite{terraform2024hashicorp}---an open-source \acl{IaC} tool that declaratively manages cloud resources---and executed with a single \texttt{make up} command.

K3s~v1.35.2+k3s1~\cite{k3s2024rancher} is installed as the \acs{K8s} distribution. K3s was chosen over full \acs{K8s} because its lighter control-plane footprint ($\sim$600\,MB \acs{RAM}) leaves more headroom on the 8\,GB \acs{VM} for application pods and the Prometheus monitoring stack. The embedded Traefik ingress controller is disabled; services are exposed directly via NodePort for benchmark access. containerd is used as the \ac{CRI}---the standardized interface through which the kubelet communicates with the container runtime to manage pod lifecycles.

\subsection{The WasmEdge Runtime Chain}

Running \acs{Wasm} pods alongside standard \acs{OCI} pods requires configuring containerd to route \acs{Wasm} workloads through a different \acs{OCI} runtime. The full chain is:

\begin{center}
\texttt{kubelet} $\to$ \texttt{containerd} $\to$ \textit{wasmedge shim handler} $\to$ \texttt{crun~v1.22} (\texttt{--with-wasmedge}) $\to$ \texttt{WasmEdge~0.14.1} $\to$ \texttt{.wasm binary}
\end{center}

The key components in this chain are:

\begin{itemize}
    \item \textbf{crun~v1.22:} A lightweight \acs{OCI} container runtime written in C. Unlike \texttt{runc} (written in Go), crun can be compiled with \texttt{--with-wasmedge} to link against \texttt{libwasmedge.so}, enabling it to detect and execute \texttt{.wasm} binaries natively. No pre-built package includes \acs{WasmEdge} support, so crun was compiled from source as part of the \texttt{cloud-init} bootstrap script.
    \item \textbf{containerd plugin entry:} The containerd configuration registers a \texttt{wasmedge} runtime plugin that invokes crun instead of \texttt{runc}. Pod annotation forwarding (\texttt{run.oci.handler} and \texttt{module.wasm.image/variant}) is configured to allow \acs{K8s} pod annotations to reach crun.
    \item \textbf{WasmEdge~0.14.1:} Installed system-wide. The \acs{WasmEdge} library (\texttt{libwasmedge.so}) is used by crun at pod startup to \acs{JIT}-compile the \texttt{.wasm} binary and execute it.
\end{itemize}

\subsection{Observability Stack}

Observability refers to the ability to infer the internal state of a system from its external outputs---primarily metrics, logs, and traces. In this experimental context, observability is required to collect the quantitative performance metrics defined in Chapter~\ref{chap:methodology} (memory, \acs{CPU}, request latency, and throughput) from all four variants simultaneously and under identical conditions.

The \texttt{kube-prometheus-stack} Helm chart is deployed into the \texttt{observability} namespace, providing Prometheus~\cite{prometheus2024cncf} (NodePort~32090, 5\,s scrape interval, 7-day retention, 10\,Gi \acs{PVC}) and Grafana (NodePort~32000). A 5-second scrape interval was chosen to capture sub-second metric resolution during the 60-second k6 load window. Node Exporter provides host-level \acs{CPU} and memory metrics; the \texttt{cAdvisor} integration in containerd exposes per-container \texttt{container\_memory\_rss} and \texttt{container\_cpu\_usage\_seconds\_total} metrics.

\subsection{Infrastructure as Code}

The entire environment is described declaratively:

\begin{itemize}
    \item \textbf{Terraform} provisions the Hetzner Cloud firewall (restricting \acs{SSH} and \acs{K8s} \acs{API} access to the operator's \acs{IP}) and the ccx13 \acs{VM}.
    \item \textbf{cloud-init} installs K3s, \acs{WasmEdge}, compiles crun, and configures containerd on first boot. The complete environment, from bare cloud \acs{VM} to a functioning dual-runtime \acs{K8s} cluster with observability, is bootstrapped with \texttt{make up \&\& make configure \&\& make deploy-stack}.
\end{itemize}

\section{Reference Workload: Sieve of Eratosthenes}
\label{sec:reference_workload}

The Sieve of Eratosthenes is a classical algorithm for finding all prime numbers up to a given limit $N$. The implementation marks composite numbers by iterating through multiples of each discovered prime, completing in $O(N \log \log N)$ time with $O(N)$ space. All four variants implement the identical algorithmic logic; the only differences are the \acs{HTTP} framework and I/O model.

The \acs{HTTP} \acs{API} is:
\begin{verbatim}
GET /prime?limit=N&no_list=1
\end{verbatim}
where \texttt{limit} is capped at 10,000,000 across all variants. The \acs{JSON} response contains the fields \texttt{runtime}, \texttt{limit}, \texttt{count}, and \texttt{elapsed\_us}. The \texttt{elapsed\_us} field measures only the sieve computation, not network or serialization time. The \texttt{no\_list} flag suppresses the array of prime numbers, ensuring that \acs{JSON} encoding time does not confound throughput measurements.

Each variant also exposes \texttt{GET /health} returning \acs{HTTP}~200, used for \acs{K8s} liveness and readiness probes.

\section{Docker/Golang Implementation}
\label{sec:impl_docker_golang}

The docker-golang service uses Go~1.26 and the \texttt{net/http} standard library. The server is started with \texttt{http.ListenAndServe(":8080", mux)}, which creates one goroutine per accepted connection. Go's M:N scheduler multiplexes goroutines onto \acs{OS} threads, enabling concurrent request handling without explicit thread management. The sieve computation and \acs{JSON} marshaling use only standard library packages (\texttt{encoding/json}), resulting in zero external dependencies.

The Docker image uses a two-stage build: a \texttt{golang:1.26-alpine} builder stage compiles a fully static binary with \texttt{CGO\_ENABLED=0 GOOS=linux}, and a \texttt{scratch} final stage contains only the binary. The resulting image is \textbf{6.00\,MB}, the largest of the four variants due to Go's compiled-in runtime metadata (goroutine scheduler, garbage collector, standard library \acs{DWARF} symbols).

\section{Docker/Rust Implementation}
\label{sec:impl_docker_rust}

The docker-rust service uses Rust~1.94 with the axum~0.8 web framework running on the Tokio async runtime. The \texttt{\#[tokio::main]} macro spawns a multi-threaded executor whose thread count equals the number of available \acs{CPU} cores. Axum's async handler model allows all 50 concurrent k6 \acp{VU} to be processed in parallel, with each handler awaiting the sieve computation in its own async task.

The Docker image uses a two-stage build: a \texttt{rust:1.94-slim} builder stage with \texttt{cargo build --release} (link-time optimisation enabled, \texttt{codegen-units=1}, \texttt{opt-level=3}, binary stripped), and a \texttt{scratch} final stage. The resulting image is \textbf{2.08\,MB}---3$\times$ smaller than docker-golang, reflecting Rust's lack of a garbage collector and the absence of any bundled runtime metadata.

\section{Wasm/Rust Implementation}
\label{sec:impl_wasm_rust}

\subsection{HTTP Stack Selection and Ecosystem Friction}

Implementing an \acs{HTTP} server in Rust targeting \texttt{wasm32-wasip1} required navigating a significant ecosystem gap. The evaluation proceeded through four candidate approaches before a working solution was found (as documented in \hyperref[chap:methodology]{Chapter~\ref{chap:methodology}, Section~\ref{sec:tech_selection}}). The only viable path was \texttt{wasmedge\_wasi\_socket~0.5.5}~\cite{wasmedgewasisocket}, a \acs{WasmEdge}-specific crate that imports \acs{WasmEdge}'s proprietary \acs{TCP} socket host functions directly from \texttt{wasi\_snapshot\_preview1}.

\subsection{Single-Threaded Accept Loop}

Because \texttt{wasmedge\_wasi\_socket} provides only synchronous, blocking socket operations, the server is structured as a single-threaded accept-handle-respond loop. The entry point of the service is:

\begin{verbatim}
fn main() {
    let listener = TcpListener::bind("0.0.0.0:8080", false)
        .expect("failed to bind");
    for stream in listener.incoming() {
        match stream {
            Ok(s)  => handle_connection(s),
            Err(e) => eprintln!("accept error: {e}"),
        }
    }
}
\end{verbatim}

Each call to \texttt{handle\_connection} reads the full \acs{HTTP} request, executes the sieve, and writes the response before the loop accepts the next connection. There is no buffering, no connection pool, and no concurrency within the process. Under concurrent load, incoming connections queue at the \acs{TCP} level; connections that wait longer than k6's default timeout are reported as failures.

This is a fundamental architectural constraint of \acs{WASI}~P1, not a limitation of Rust. \acs{WASI}~P2's \texttt{wasi:http} world provides a fully asynchronous \acs{HTTP} handler interface that would eliminate this bottleneck.

\subsection{Build and Packaging}

The \texttt{.wasm} binary is compiled with \texttt{cargo build --target wasm32-wasip1 --release}. The cargo profile enables \acs{LTO} and \texttt{codegen-units=1} for maximal optimisation. The resulting binary is wrapped in a minimal \acs{OCI} image using a \texttt{scratch} base: the image layer contains only the \texttt{app.wasm} binary. The final image size is \textbf{0.13\,MB}---16$\times$ smaller than the docker-rust variant using the same language and algorithm. This dramatic size reduction reflects the \acs{Wasm} binary format's elimination of all \acs{OS} userland, libc, and binary format overhead.

\section{Wasm/TinyGo Implementation}
\label{sec:impl_wasm_tinygo}

\subsection{TinyGo HTTP Stack Limitation}

TinyGo~0.40.1~\cite{tinygo2024} targeting \texttt{wasm32-wasip1} encounters a critical limitation: \texttt{net/http}'s server-side code path has been non-functional on \texttt{wasip1} since TinyGo~0.28, when the Netdev network architecture was refactored in a way that permanently broke \texttt{ListenAndServe} for the \acs{WASI} target. Compiling the service with \texttt{http.ListenAndServe} either panics at runtime or fails silently without binding a socket.

\subsection{Raw WasmEdge Socket Imports}

The solution is a custom \texttt{server.go} file that directly imports \acs{WasmEdge}'s \acs{TCP} socket host functions via Go's \texttt{//go:wasmimport} directive:

\begin{verbatim}
//go:wasmimport wasi_snapshot_preview1 sock_open
func sock_open(af int32, socktype int32, fd unsafe.Pointer) int32
\end{verbatim}

This pattern bypasses the \texttt{net/http} abstraction entirely, calling \acs{WasmEdge}'s \acs{WASI} snapshot preview socket functions (\texttt{sock\_open}, \texttt{sock\_bind}, \texttt{sock\_listen}, \texttt{sock\_accept}, \texttt{sock\_recv}, \texttt{sock\_send}) at the \acs{ABI} level. The \texttt{main.go} file retains the familiar Go \acs{HTTP} handler pattern (\texttt{http.HandleFunc}, \texttt{http.ResponseWriter}), but the transport layer routes through the custom socket implementation.

The \texttt{-gc=conservative} build flag is required: TinyGo's conservative garbage collector scans the stack for pointers without moving objects, ensuring that \texttt{unsafe.Pointer} values passed to the \acs{WasmEdge} socket \acs{ABI} remain valid for the duration of the host function call.

\subsection{Build and Packaging}

The binary is compiled with:
\begin{verbatim}
tinygo build -target=wasi -gc=conservative -opt=2 -o app.wasm .
\end{verbatim}
The resulting image is \textbf{2.26\,MB}---slightly larger than docker-rust despite targeting \acs{Wasm}---because TinyGo bundles its own minimal Go runtime (scheduler stub, conservative \acs{GC}, standard library subset) inside the \texttt{.wasm} binary.

\section{Kubernetes Deployment Configuration}
\label{sec:k8s_deployment}

All four variants are deployed into the \texttt{prime-sieve} namespace. Each variant has a \texttt{Deployment} (1 replica) and a \texttt{Service} of type \texttt{NodePort}.

\textbf{Docker variants} use standard \texttt{Deployment} manifests with no \texttt{runtimeClassName}; containerd routes these pods through the default \texttt{runc} path.

\textbf{Wasm variants} require three additional fields. The pod \texttt{spec} sets \texttt{runtimeClassName: wasmedge}. The pod \texttt{metadata.annotations} include \texttt{run.oci.handler: wasmedge} and \texttt{module.wasm.image/variant: compat}. The container \texttt{command} is set to \texttt{["/app.wasm"]}. These annotations are forwarded by containerd to crun, which uses them to detect and delegate execution to \acs{WasmEdge} rather than attempting to execute the binary as a Linux \acs{ELF} executable.

Each variant's \texttt{Deployment} specifies identical resource requests and limits to ensure a level playing field: \texttt{requests} of 250m \acs{CPU} and 64\,MiB memory, and \texttt{limits} of 1000m \acs{CPU} (1 vCPU) and 512\,MiB memory. Setting a uniform \acs{CPU} limit ensures that no variant can monopolize the shared 2-vCPU host. An important runtime consideration applies to the Docker variants: by default, Go's runtime sets \texttt{GOMAXPROCS} equal to the number of \textit{visible} host \acs{CPU} cores (2), not the container's \acs{CPU} limit. Similarly, Tokio's multi-threaded executor spawns one worker thread per visible core. Both runtimes therefore observe 2 cores despite the 1-vCPU limit, which the kernel enforces via \acs{CPU} bandwidth throttling. This is documented as a known measurement constraint; future work should explicitly set \texttt{GOMAXPROCS=1} and \texttt{TOKIO\_WORKER\_THREADS=1} to fully eliminate this variable.

Liveness and readiness probes execute \texttt{GET /health} with a 30-second initial delay to allow \acs{WasmEdge}'s \acs{JIT} compilation to complete before the pod is declared ready.
