\chapter{Background}
\label{chap:background}

This chapter provides the foundational technical context required to evaluate the comparative analysis presented in this thesis. It traces the evolution of computing infrastructure from on-premises hardware to modern cloud paradigms, details the mechanics of containerization and orchestration, and culminates in a comprehensive architectural breakdown of \ac{Wasm} as an emerging server-side execution environment.

\section{Cloud Computing and Microservices}
\label{sec:cloud_microservices}

\subsection{The Evolution of Cloud Paradigms}
The genesis of modern software deployment traces back to on-premises data centers, where organizations were solely responsible for the procurement, maintenance, and scaling of physical hardware. This capital-heavy model suffered from severe resource underutilization; servers were provisioned for peak load, leaving them idle during standard operations. The modern cloud computing era shifted the industry to a pay-as-you-go, scalable operational model, fundamentally altering how infrastructure is managed~\cite{mell2011nist}.

As cloud computing matured, the industry developed a ``Shared Responsibility Model,'' where the abstraction layer moved progressively higher up the stack. As illustrated in Figure~\ref{fig:iaas_paas_faas_saas}, this spectrum dictates whether the cloud provider or the client is responsible for specific layers of the technological stack:

\begin{itemize}
    \item \textbf{\acl{IaaS} (\acs{IaaS}):} The cloud provider manages the physical hardware, storage, and networking. The client rents virtualized infrastructure (e.g., a \acl{VM}) and retains full responsibility for managing the operating system, middleware, language runtimes, and the application code itself. This offers maximum control but requires significant operational overhead.
    \item \textbf{\acl{PaaS} (\acs{PaaS}):} The provider abstracts both the underlying hardware and the operating system. The client is provided a managed environment and is solely responsible for deploying their application code and managing their data. Traditional Docker container deployments often operate in this space.
    \item \textbf{\acl{FaaS} (\acs{FaaS}) / Serverless:} The highest level of \textit{infrastructure} abstraction for a developer. The cloud provider dynamically manages the allocation, provisioning, and scaling of the servers and runtimes. The client writes granular, event-driven functions and dictates the trigger configurations. Crucially, \acs{FaaS} allows applications to ``scale to zero,'' eliminating compute costs during periods of inactivity~\cite{jonas2019cloud}.
    \item \textbf{\acl{SaaS} (\acs{SaaS}):} The highest level of \textit{software} abstraction. The cloud provider hosts and manages the entire application stack. The client manages nothing regarding the deployment or execution environment; they simply consume the finished software over the internet.
\end{itemize}

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.8\textwidth]{figures/iaas_paas_faas_saas.pdf}
    \caption{The Shared Responsibility Model across varying Cloud Computing Paradigms.}
    \label{fig:iaas_paas_faas_saas}
\end{figure}

For the purposes of this research, \acs{SaaS} falls outside the scope of architectural implementation. The critical transition lies between \acs{PaaS} and \acs{FaaS}. The relentless industry drive toward rapid elasticity, microsecond billing, and extreme resource efficiency in \acs{FaaS} and edge environments exposed the limitations of traditional, heavy deployment artifacts. Standard \acs{OCI} containers, laden with operating system userlands, introduce severe latency bottlenecks in these paradigms, necessitating a shift toward the lightweight isolation models that \acs{Wasm} provides.

\subsection{Microservice Architecture}
Microservice architecture emerged as the logical software design pattern for cloud-native deployment. Unlike traditional monolithic applications---where all business logic, user interfaces, and database connections are tightly coupled into a single executable---microservices decompose an application into a collection of small, independently deployable, and loosely coupled services that communicate over a network via language-agnostic \acp{API}~\cite{newman2015building}.

This paradigm offers distinct advantages: development agility, localized fault isolation, and the ability to scale specific system bottlenecks independently. However, it introduces severe distributed system challenges. Managing network latency, data consistency, and the operational overhead of packaging and deploying hundreds of individual services necessitated the creation of entirely new virtualization and orchestration layers.

\section{Containerization and Orchestration}
\label{sec:containerization}

\subsection{Virtual Machines vs. Containers}
To solve the deployment complexity of microservices, the industry initially relied on \acp{VM}. However, \acp{VM} require a hypervisor to emulate physical hardware, atop which a complete guest \ac{OS} is installed. This results in gigabytes of memory overhead and startup times measured in minutes, making them inherently unsuitable for transient, rapidly scaling microservices.

Docker revolutionized the landscape by democratizing Linux containers. Instead of virtualizing the hardware, containers virtualize the operating system~\cite{merkel2014docker}. As shown in Figure~\ref{fig:virtual_machine_vs_docker}, Docker relies on two core Linux kernel features:
\begin{enumerate}
    \item \textbf{Namespaces:} Provide process isolation, ensuring the container has its own isolated filesystem, network interfaces, and process tree.
    \item \textbf{Cgroups (Control Groups):} Limit, isolate, and monitor the resource usage (\ac{CPU}, memory, disk I/O) of a given process.
\end{enumerate}

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{figures/virtual_machine_vs_docker.pdf}
    \caption{Infrastructure Isolation Models: Virtual Machines vs.\ Docker Containers}
    \label{fig:virtual_machine_vs_docker}
\end{figure}

Docker's definitive innovation was the standardization of the container image format, now governed by the \ac{OCI}. By packaging application code alongside its dependencies, libraries, and a base filesystem into a single portable unit, Docker ensured environment consistency from a developer's laptop to production servers.

Despite its dominance, the \acs{OCI} standard has inherent drawbacks. Because containers share the host's Linux kernel, a kernel-level vulnerability can potentially compromise all containers on that host, posing security risks in multi-tenant environments. Furthermore, traditional container images are bulky; they bundle a userland \acs{OS} and language runtimes alongside the application. This bulk introduces latency during image transfer and initialization---known as the ``cold start'' problem---which is highly detrimental in \acs{FaaS} and edge computing environments~\cite{gadepalli2020challenges}.

\subsection{Kubernetes Orchestration}
As microservices proliferated, manually managing individual containers across a fleet of servers became operationally unfeasible. \ac{K8s} emerged as the industry-standard container orchestration platform. It abstracts the underlying cluster of hardware, allowing engineers to declare the desired state of their applications rather than manually scripting deployments~\cite{burns2016borg}.

\acs{K8s} operates on a distributed architecture, as depicted in Figure~\ref{fig:kubernetes_architecture}. The Control Plane dictates instructions to worker nodes. Each worker node runs an agent called a Kubelet, which manages Pods---the smallest deployable computing unit, typically containing one or more tightly coupled containers. Crucially, \acs{K8s} communicates with the underlying container runtime (like containerd or CRI-O) via the \ac{CRI}. This decoupled architecture established strict standardizations, eventually allowing alternative, non-Linux execution environments, such as \acs{Wasm}, to be orchestrated seamlessly alongside standard \acs{OCI}-compliant containers.

\section{WebAssembly}
\label{sec:wasm}

\subsection{Origin and Technical Architecture}
\ac{Wasm} is a binary instruction format designed for a stack-based virtual machine. It originated from the need to execute high-performance code within web browsers---a domain historically constrained by JavaScript's inconsistent performance and parsing overhead. \acs{Wasm} was officially released in 2017 as a \ac{W3C} standard, sitting alongside \ac{HTML}, \ac{CSS}, and JavaScript as an official language of the web~\cite{haas2017bringing}.

\acs{Wasm} functions as an agnostic hardware abstraction layer. Developers write code in systems languages like C, C++, or Rust and compile it down to \texttt{.wasm} binaries, as illustrated in Figure~\ref{fig:compiling_different_langauges_to_wasm}. Beyond these systems languages, \acs{Wasm} serves as a compilation target for more than 40 programming languages~\cite{fermyon2024langmatrix}, including Go, Python, Kotlin, C\#, and TypeScript, with varying degrees of ecosystem maturity across \acs{WASI} runtimes.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.5\textwidth]{figures/languages_compile_to_wasm.pdf}
    \caption{A selection of programming languages that compile to \acs{Wasm}, illustrating its language-agnostic compilation model.}
    \label{fig:compiling_different_langauges_to_wasm}
\end{figure}

\subsection{Module Structure and Stack-Based Execution}
\acs{Wasm} is fundamentally a stack machine. Unlike register-based physical \ac{CPU} architectures (such as x86\_64 or ARM64), \acs{Wasm} instructions implicitly operate on an operand stack. Variables are pushed onto the stack, and operations pop these operands, compute the result, and push it back. This design yields highly compact binary modules, as instructions do not need to explicitly encode register numbers, accelerating both transmission over networks and decoding phases.

A \acs{Wasm} application is distributed as a strictly standardized binary module consisting of discrete sections. These include the Type section (function signatures), Import section (host-provided dependencies), Code section (executable bytecode), and Data section (initial memory state). Before execution, a \acs{Wasm} runtime performs a deterministic, single-pass validation to ensure type safety and structural integrity. Because the bytecode is designed to map cleanly to native machine instructions, runtimes employ \ac{JIT} or \ac{AOT} compilation engines (such as Cranelift or LLVM) to translate \acs{Wasm} into highly optimized, native machine code instantaneously.

\subsection{Memory Management and Isolation}
One of \acs{Wasm}'s defining technical characteristics is its approach to memory management and fault isolation. The architecture relies on the following core principles:
\begin{itemize}
    \item \textbf{Compact Binary Format:} The \texttt{.wasm} format is highly optimized, allowing for rapid fetching, decoding, and execution.
    \item \textbf{Hardware Agnosticism:} Because it utilizes a virtual stack machine, the compiled bytecode makes no assumptions about the underlying physical \acs{CPU} architecture, enabling true portability across varied cloud node pools.
    \item \textbf{Linear Memory Space:} \acs{Wasm} operates in a contiguous, resizable array of bytes known as linear memory. Code executing within the \acs{Wasm} module operates strictly with integer offsets within this array; it cannot execute arbitrary pointers or access host memory outside this strictly enforced boundary.
    \item \textbf{\acl{SFI} (\acs{SFI}):} Unlike Docker, which relies on the host \acs{OS} kernel (cgroups/namespaces) to contain a process, \acs{Wasm} achieves isolation mathematically at the runtime level. Any attempt to access memory outside the allocated linear boundary results in a deterministic trap, halting the module instantly without compromising the host.
\end{itemize}

\subsection{Language Agnosticism and the JVM Comparison}
The concept of \ac{WORA} was popularized by Java. Java achieves portability by compiling source code to Java bytecode, which is executed by the \ac{JVM}. However, \acs{Wasm} fundamentally differs from the \acs{JVM} in design and scope, as illustrated in Figure~\ref{fig:java_vs_wasm}. The \acs{JVM} was built specifically to execute Java and inherently carries a heavyweight runtime featuring built-in garbage collection. Conversely, \acs{Wasm} was designed as a low-level, truly language-agnostic compilation target without an opinionated runtime, making it exceptionally lightweight.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.7\textwidth]{figures/java_vs_wasm.pdf}
    \caption{An analogy comparing the cross-platform execution models of Java (\acs{JVM}) and \acs{Wasm}. Adapted from Chiarlone~\cite{chiarlone2024serverside}.}
    \label{fig:java_vs_wasm}
\end{figure}

For languages requiring automatic memory management (like Go, Python, Kotlin, or PHP), \acs{Wasm} historically required the entire language runtime and garbage collector to be compiled and bundled inside the \texttt{.wasm} binary. This approach bloated the deployment artifact and created redundant layers of memory management. For instance, deploying a compiled-to-\acs{Wasm} language with its own garbage collector into a host environment that already possesses one (such as a browser engine like V8) is highly wasteful~\cite{steiner2023wasmgc}. Furthermore, having no interaction between \acs{Wasm}'s linear memory and the built-on-top garbage collector of the ported language often caused problems like memory leaks and inefficient collection attempts~\cite{liedtke2023v8wasmgc}.

To resolve this, the \ac{WasmGC} standard has been introduced to delegate memory management directly to the host environment. \acs{WasmGC} extends the \acs{Wasm} memory model by adding struct and array heap types, thereby providing native support for non-linear memory allocation~\cite{wasm2023gcproposal}. Because each \acs{WasmGC} object has a fixed type and structure, host \acp{VM} can generate highly efficient access code without the risk of dynamic deoptimizations. This allows higher-level managed languages to bypass bundling their own garbage collectors, instead interfacing efficiently with the host \acs{VM}'s built-in garbage collector.

The architectural impact on artifact density is significant. By eliminating the need to bundle memory management code, \acs{WasmGC} binaries for managed languages can achieve dramatically smaller footprints. In early benchmarks, \acs{WasmGC} binaries for languages like Java were proven to be considerably smaller than equivalent modules compiled from C or Rust, because C and Rust must still bundle manual memory management routines like \texttt{malloc} and \texttt{free} inside the binary~\cite{steiner2023wasmgc}. This advancement firmly positions \acs{Wasm} as a viable, high-density target for the entire spectrum of modern programming languages.

\subsection{The Server-Side Evolution: WASI}
While \acs{Wasm} successfully delivered near-native performance for computationally heavy browser applications, its portability, mathematical security model, and minimal footprint rapidly garnered interest for backend deployment. Solomon Hykes, the founder of Docker, once famously stated:
\begin{quote}
    If WASM+WASI existed in 2008, we wouldn't have needed to create Docker. That's how important it is. WebAssembly on the server is the future of computing.~\cite{hykes2019tweet}
\end{quote}

Because \acs{Wasm} is entirely isolated by default, a bare \acs{Wasm} module running on a server cannot open a network socket, read a file, or query the system clock. In 2019, the \acl{WASI} was introduced to solve this. \acs{WASI} defines a standardized \acs{API} specification that provides \acs{Wasm} modules with secure, granular, capability-based access to the host operating system~\cite{clark2019standardizing}. By acting as a secure \acs{POSIX}-like layer, \acs{WASI} transforms \acs{Wasm} from a sandboxed browser calculator into a fully functional server-side technology.

\subsection{Capability-Based Security Model}
\acs{WASI} implements a capability-based security model that diverges significantly from traditional Linux permissions. A Linux container limits an already-running \acs{OS} environment. \acs{WASI}, however, enforces a strict ``deny-by-default'' posture embodying the \ac{POLA}.

If a \acs{Wasm} module needs to access a configuration file, it cannot invoke a standard \texttt{open()} system call for an arbitrary path (e.g., \texttt{/etc/config}). Instead, the host runtime must explicitly grant the module a ``pre-opened'' file descriptor at startup. The module is completely blind to the existence of the host filesystem outside the specific directory tree explicitly mapped and passed to it by the runtime. Figure~\ref{fig:wasm_sandboxed_model} contrasts this capability-based model with the traditional Linux permission model.

\subsection{Architectural Evolution: From POSIX to the Component Model}
The initial iteration of \acs{WASI} (Preview~1) was heavily modeled after standard \acs{POSIX} interfaces, focusing on file descriptors, environment variables, and standard I/O streams. While effective for simple command-line tools and basic microservices, this \acs{POSIX}-centric approach introduced friction when handling complex, multi-language cloud-native interactions.

To address this, the \acs{Wasm} ecosystem is currently transitioning to the WebAssembly Component Model (\acs{WASI} Preview~2 and Preview~3). The Component Model shifts \acs{WASI} from a low-level \acs{POSIX} \acs{API} to a high-level, language-agnostic interface system utilizing \ac{WIT}. This advancement allows discrete \acs{Wasm} components---potentially written in entirely different source languages---to natively interoperate. They can securely pass complex data types (such as strings, records, and variants) across execution boundaries without sharing linear memory, laying the foundation for highly modular, secure, and dynamically composable microservice architectures.

Critically for server-side applications, \acs{WASI} Preview~2 introduces \texttt{wasi:http} and \texttt{wasi:io/poll}, which together enable asynchronous, event-driven \acs{HTTP} servers within \acs{Wasm} modules~\cite{bytecodealliance2024componentmodel, clark2023preview2}. This directly resolves the single-threaded \acs{HTTP} handling limitation present in \acs{WASI} Preview~1, which is a central finding of this thesis. The experiments in this work target \acs{WASI} Preview~1 exclusively, as it remains the production-deployed standard for the runtimes and \acs{K8s} integrations used here; the Component Model represents the intended future direction.

\subsection{Wasm vs. Traditional Containers}
Applying \acs{Wasm} and \acs{WASI} to the server yields a deployment artifact that sits functionally between a traditional \acs{VM} and an \acs{OCI} container, offering unique operational characteristics:

\begin{enumerate}
    \item \textbf{Cold Start and Footprint:} Traditional \acs{OCI} containers bundle an \acs{OS} userland, frequently resulting in image sizes exceeding 100\,MB and startup times measured in seconds. A \acs{Wasm} module contains only the compiled application logic. \acs{Wasm} binaries are typically just a few megabytes and can be instantiated by a host runtime in microseconds. Long~et~al.\ demonstrated that \acs{Wasm} runtimes can perform at least 10$\times$ faster than Docker from a cold start for short-running workloads~\cite{long2023wasm}. Hall and Ramachandran further verified that \acs{Wasm}'s improved cold start times lead to up to 90\% faster response times for basic serverless tasks~\cite{hall2021serverless}.
    \item \textbf{Security and Density:} \acs{Wasm} utilizes \acs{SFI}. If a \acs{Wasm} module is compromised, the attacker only controls the isolated linear memory sandbox. Because \acs{Wasm} modules do not require full \acs{OS} process overhead, the minimal memory footprint allows \acs{K8s} nodes to achieve exponentially higher workload density.
    \item \textbf{Performance Trade-offs:} Despite its advantages in density and initialization, \acs{Wasm} presents concurrency constraints in its \acs{WASI} Preview~1 incarnation. \acs{Wasm} itself has a ratified Threads proposal~\cite{wasmthreadsproposal} supported across all major browsers and runtimes, but \acs{WASI} Preview~1 does not expose thread-spawning primitives to server-side \acs{Wasm} modules, leaving them constrained to single-threaded execution. Sondell (2024) demonstrated that in high-concurrency \acs{HTTP} server scenarios, a Docker container can process requests significantly faster because it can scale natively across multiple \acs{CPU} cores, whereas a single \acs{Wasm} instance operating under \acs{WASI}~P1 remains bottlenecked by sequential request processing~\cite{sondell2024performance}. Furthermore, Spies and Mock found that single-threaded \acs{Wasm} applications perform approximately 14\% slower than native x86\_64 binaries due to sandbox bounds-checking overhead~\cite{spies2021evaluation}.
\end{enumerate}

By utilizing \acs{WASI} shims (such as \texttt{runwasi}), \acs{K8s} can now orchestrate these high-density \acs{Wasm} workloads directly alongside traditional Docker containers, establishing the precise technological foundation for the comparative analysis executed in this research.
