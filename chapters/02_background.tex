\section{WebAssembly (Wasm)}
\label{sec:wasm}
\subsection{Origin and Overview}
WebAssembly was originally announced in 2015 as a portable, size- and load-time-efficient format suitable for compilation to the web. It was designed to enable high-performance applications on web pages.
\subsection{Technical Details}
\begin{itemize}
    \item \textbf{Binary Format:} Wasm uses a compact binary format that is fast to decode.
    \item \textbf{Stack Machine:} It is defined as a virtual stack machine, unrelated to the physical machine architecture.
    \item \textbf{Linear Memory:} Security is enforced through a linear memory model that prevents the code from accessing memory outside its sandbox.
    \item \textbf{Isolation:} The host environment is completely isolated from the module unless imports are explicitly defined.
\end{itemize}
\subsection{Phase 1: Frontend and Browser Adoption}
Initially, Wasm was used to port C/C++ applications (like game engines, video editors, and image processors) to the browser, allowing them to run at near-native speed alongside JavaScript.
\subsection{Phase 2: Server-Side WebAssembly}
The "Second Phase" of Wasm involves moving it out of the browser. This section explores why Wasm is ideal for the server side:
\begin{itemize}
    \item \textbf{Security:} Default sandboxing makes it safer for multi-tenant environments.
    \item \textbf{Portability:} "Write once, run anywhere" (creating true universal binaries).
    \item \textbf{Performance:} Near-instant startup times compared to booting a full container OS.
\end{itemize}
\subsection{WASI (WebAssembly System Interface)}
A critical standard that allows Wasm modules to access system resources (files, network, clocks) in a standardized, secure way, enabling server-side execution.
